# Gemini Code Assist Style Guide

## 언어

- 리뷰 요약, 리뷰 코멘트, 수정 제안 설명은 한국어로 작성합니다.
- 코드 식별자, 파일 경로, 명령어, 패키지명은 원문 영어를 유지합니다.

## PR 리뷰 기준

- 기존 프로젝트 컨벤션과 문서화된 규칙을 우선합니다.
- Java, Spring Boot, Gradle, MySQL, JPA(Hibernate) 기반 백엔드 프로젝트임을 전제로 리뷰합니다.
- Controller는 요청 수신, 입력 검증, 서비스 위임, 응답 반환만 담당하는지 확인합니다.
- 비즈니스 로직은 Domain 또는 Service 계층에 있는지 확인합니다.
- 불필요한 추상화와 과한 설계를 권장하지 않습니다.
- 테스트 누락, 예외 처리 누락, 보안 위험, 동작 회귀 가능성을 우선적으로 지적합니다.

## PR 제목

- PR 제목은 `<type>: <변경 요약>` 형식을 따릅니다.
- 허용 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`입니다.
- PR의 주된 변경 목적을 기준으로 타입을 선택합니다.
- 설정, 도구, 자동화, 하네스, 운영성 변경이 주 목적이면 `chore`를 사용합니다.
- 테스트 코드가 함께 포함되어도 주된 목적이 설정 검증이면 `chore`를 사용합니다.
- 변경 요약은 `추가`, `수정`, `보강`, `분리`, `정리`, `개선` 같은 짧은 제목형으로 작성합니다.
- PR 제목은 마침표로 끝내지 않습니다.

예:

- `feat: 상품 조회 API 추가`
- `fix: 인증 토큰 만료 처리 수정`
- `refactor: 결제 승인 서비스 책임 분리`
- `test: 인증 컨트롤러 예외 응답 테스트 추가`
- `docs: 상품 조회 API 문서 보강`
- `chore: PR 템플릿 리뷰 반영`

## 커밋 메시지

- 커밋 메시지는 `<type>: <subject>` 형식을 따릅니다.
- 허용 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`입니다.
- `subject`는 `~~한다` 형태의 한국어 현재형 문장으로 작성합니다.
- `subject`는 마침표로 끝내지 않습니다.
- 하나의 커밋은 하나의 논리적 변경만 담아야 합니다.
- `Update <file>`처럼 파일명만 설명하는 메시지는 사용하지 않습니다.
- 변경 의도가 드러나도록 작성합니다.

예:

- `feat: 상품 조회 API를 추가한다`
- `fix: 인증 토큰 만료 처리를 수정한다`
- `refactor: 결제 승인 서비스 책임을 분리한다`
- `test: 인증 컨트롤러 예외 응답 테스트를 추가한다`
- `docs: 상품 조회 API 문서를 보강한다`
- `chore: Gemini 코드 리뷰 설정을 추가한다`

## Gemini suggestion 커밋 메시지

- Gemini Code Assist가 리뷰 코멘트에서 suggestion을 제안할 때도 이 저장소의 커밋 메시지 규칙을 따릅니다.
- suggestion 적용으로 생성되는 커밋 메시지 또는 커밋 제목은 `<type>: <subject>` 형식으로 작성합니다.
- suggestion 커밋의 `subject`도 `~~한다` 형태의 한국어 현재형 문장으로 작성합니다.
- suggestion 커밋 메시지를 `Apply suggestion`, `Update <file>`, `Fix issue`처럼 일반적인 기본 문구로 작성하지 않습니다.
- 예: `fix: 인증 예외 응답 상태 코드를 수정한다`

## 테스트

- 기본 테스트 명령은 `./gradlew test`입니다.
- 현재 `./gradlew test`는 `concurrency`, `test`, `batch` 태그 테스트를 제외합니다.
- 태그 제외 테스트가 변경 범위에 관련되면 별도 실행 필요성을 언급합니다.
