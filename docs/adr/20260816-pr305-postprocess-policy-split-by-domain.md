# 후처리 판정 정책을 결제용과 환불용으로 나눈다

- Status: accepted
- Date: 2026-08-16

## Context

후처리 판정 정책은 대사가 집은 건을 무엇으로 분류할지(재조회·재전송·관리자 확인·대상 아님) 정하는 곳이다. 그 정책이 **옛 테이블 구조를 세 군데서 전제하고 있었다.** 승인 결제와 취소 결제가 같은 테이블의 두 행이었으므로 한 함수가 둘을 받았고, 분류값에 승인·취소 접두어가 붙었으며, 최종 실패한 건이 재조회 대상이었다.

결제와 환불이 다른 엔티티가 되면서 **애초에 한 함수가 둘을 받을 수 없다.** 상태 집합도 갈라졌고, 환불에는 결제에 없는 행위가 하나 더 있다.

## Decision

**정책을 결제용과 환불용으로 나눈다.** 각자 자기 상태 집합만 보고, 분류값에서 승인·취소 접두어를 걷어낸다. 환불 정책에는 **"보낸다"**가 하나 더 있다 — 옛 모델에는 아직 안 보낸 환불이 없었다.

옛 구조를 전제한 분기 셋을 걷어낸다.

| 걷어내는 분기 | 왜 |
| --- | --- |
| 결제 실패 + 취소 행 없음 → 보상 생성 | 승인 반려가 **결제 종결과 환불 생성을 한 트랜잭션으로** 커밋하므로 잔여가 없다 |
| 중복 결제 관련 | **활성 슬롯이 그 상태를 원천에서 막는다** |
| 최종 실패 + 실패 코드 → 재조회 | 옛 모델의 "최종 실패"는 이번 시도의 실패였다. 새 모델에서는 **시도의 실패가 사건의 실패가 아니라** 사건이 진행 중에 머물고, 자동으로 더 못 가는 건은 사람이 처리하는 상태로 간다 |

## Consequences

**같은 이름의 분류가 두 도메인에서 다르게 동작한다** — 결제의 관리자 확인은 "알린다"이고 그 뒤에도 결과 회수를 계속하지만, 환불의 관리자 확인은 "알리고 자동 처리를 멈춘다"이다. 정책을 나눴으므로 각 enum이 자기 도메인 안에서만 뜻을 가져 이 차이가 자연스러워진다. 한 enum에 뭉쳐 있으면 "왜 같은 값인데 다르게 도나"가 된다.

두 정책이 갈라지면서 공통 규칙을 고칠 때 두 곳을 손봐야 한다. 그 대가를 감수한다 — 묶어 두면 한쪽에만 필요한 분기가 다른 쪽 판정 경로에 계속 남는다.

세 번째로 걷어낸 분기의 근거는 **앞으로 만들 모델**이다. 지금 돌아가는 코드가 아니라 새 상태 규칙을 따라간 것이라, 구현이 그 규칙에서 틀어지면 잡아 줄 그물이 하나 줄어든다.
