# 도메인 정책은 애노테이션 없이 두고 응용 계층의 등록 전용 자리에서 빈으로 만든다

- Status: accepted
- Date: 2026-08-16

## Context

후처리 판정 정책이 **도메인에 앉는다.** 상태와 시각을 받아 분류값을 돌려주는 순수한 판단이라 그 자리가 맞다.

그런데 그 정책이 **설정에서 오는 값을 들어야 한다** — 대사 유예, 다시 집는 간격표, 통지 승급 시간, 통지 반복 간격이다. 대사하는 쪽과 판정하는 쪽이 같은 값을 각자 들면 갈라지므로 한쪽이 정본이어야 하고, 판정하는 쪽이 그 값을 갖는 것이 자연스럽다. **그래서 정책이 빈이어야 하고, 등록할 방법이 필요하다.**

**"도메인은 Spring을 참조하지 않는다"가 이 선택을 대신 정해 주지는 않는다.** 확인해 보니 그렇다.

```
ArchUnit이 domain에 금지하는 것
    org.springframework.transaction · kafka · data.redis · http · web
    EntityManager · EntityManagerFactory
        ↑ org.springframework.stereotype은 없다.  @Component를 붙여도 안 걸린다

배치 규칙이 금지하는 것
    구현체에 묶인 구체 예외 (org.springframework.orm · org.hibernate · jakarta.persistence)
        ↑ 예외 타입 이야기다

domain이 이미 갖는 것
    @Entity · @Id · @Version · @Column — "선언적 매핑 메타데이터까지는 허용"이라고 밝혀 둔 입장
```

## Decision

**도메인 정책 클래스에 컨테이너 등록 애노테이션을 붙이지 않는다. 대신 응용 계층에 등록만 하는 자리를 두고 거기서 빈으로 만든다** — `application/config/`다.

**고른 이유는 설정값이다.** 정책에 애노테이션을 붙이면 등록은 되지만 **설정값을 읽는 것도 도메인이 하게 된다** — 도메인이 properties 타입이나 값 주입 방식을 알게 되고, 그 값을 바꿀 때 도메인을 건드린다. 등록하는 자리가 값을 읽어 넘기면 도메인은 **받은 값으로 판단만** 한다.

**이 계층을 나누는 축과도 맞는다.** 배치 규칙이 `application`을 책임으로 나눈다고 정했고(`usecase`=흐름 조립, `service`=트랜잭션 단위작업, `port`=나가는 인터페이스, `dto`=주고받는 값), **"빈으로 조립한다"는 또 하나의 책임**이라 앞의 넷 어디에도 안 들어간다. 이름을 `config`로 쓰는 것은 이 저장소에 이미 같은 이름의 자리가 있어 새 말이 아니기 때문이다.

## Consequences

- **도메인 정책이 순수하게 남는다.** 생성자로 받은 값으로 판단만 하므로 단위 테스트에 컨테이너가 필요 없다.
- **`@Component`를 붙이는 쪽도 규칙 위반은 아니었다.** 그 길을 안 고른 이유는 위 설정값 하나이며 **금지돼서가 아니다. 나중에 이 결정을 뒤집을 때 "규칙이 막는다"를 근거로 들지 마라.**
- **이 자리를 다른 용도로 넓히지 않는다.** 도메인 정책을 빈으로 등록하는 것까지다. 흐름을 조립하거나 트랜잭션을 여는 것이 여기 들어오면 `usecase`·`service`와 책임이 겹친다.
- **배치 규칙 문서를 고쳐야 한다.** `application` 하위 목록이 넷으로 열거돼 있어 다섯 번째가 는다. 그 갱신은 이 자리를 처음 만드는 변경에서 함께 한다 — 배치 규칙은 코드를 따라가는 것이 아니라 **이끄는** 것이라, 다음 사람이 어디에 둘지 물을 때 이미 답이 있어야 한다.
