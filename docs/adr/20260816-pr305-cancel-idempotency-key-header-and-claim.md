# 주문 취소 요청은 멱등키를 헤더로 받고 동시 도착은 선점 층이 받는다

- Status: accepted
- Date: 2026-08-16

## Context

중복 환불을 막던 "결제당 환불 행 하나" 제약이 부분환불 때문에 사라지면서, 환불 도메인이 자기 멱등 계약을 갖게 됐다. 그 키를 **서버가 결제 식별자에서 파생**하려 했는데, 그러면 같은 결제에서 나오는 값이 늘 같아 셋이 깨진다.

- 실패로 끝난 뒤 다시 환불하면 같은 값이 만들어져 유일 제약에 막힌다.
- 같은 결제에 승인 반려 환불과 회원 환불이 함께 생기면 값이 수렴해 하나로 합쳐지거나 한쪽이 거부된다.
- 값으로 기존 사건을 찾을 때 금액만 보고 누구 것인지를 보지 않는다.

무엇보다 서버 파생은 전액환불에서만 통한다. 부분환불에서는 "같은 품목 같은 수량" 요청이 두 번 왔을 때 **중복인지 진짜 두 번인지 서버가 구분할 수 없다.**

밖에서 키를 받기로 하면 "같은 값이 다시 온다"에 성질이 다른 둘이 섞인다. 앞 요청이 커밋을 끝낸 뒤 오는 순차 재요청은 `(회원, 키)` 조회가 받지만, **앞 요청이 아직 커밋 전인데 오는 동시 도착은 받는 자리가 없다.** 그 창은 앞 요청의 트랜잭션 길이만큼이고, 주문 취소는 주문 취소·환불 의도·재고 복구를 한 번에 커밋해 넓다. 비워 두면 진 쪽이 유일 제약 위반을 안전망으로 받아 서버 오류로 나가고, 셋이 어긋난다.

- **끊긴 연결 뒤 재전송에서 회원이 성공 응답을 하나도 못 받는다.** 앞 요청의 응답은 끊긴 연결로 사라졌고 재전송은 오류를 받는다. 따닥은 클라이언트가 버튼을 막아 해결하지만 **끊긴 연결은 못 막는다** — 서버 멱등키가 존재하는 이유가 이쪽이다.
- **서버 오류는 진짜 장애와 구분되지 않는다.** 클라이언트가 "이 경로의 서버 오류는 무시한다"로 짜면 결제가 실제로 안 되는 상황에서도 무시한다.
- **주문 취소는 돈이 이미 돌아가는 중인데 화면이 실패가 된다.** 회원은 취소가 안 된 줄 알고 다시 요청하는데 주문은 이미 취소돼 있다.

## Decision

**주문 취소 요청이 멱등키를 헤더로 받는다.** 주문 생성이 이미 같은 헤더를 요구하므로 형식을 맞추고, 값이 없으면 요청을 거절한다. **값으로 기존 사건을 찾을 때 요청자의 소유를 함께 확인한다** — 값만으로 찾아 돌려주면 남의 환불이 이번 요청 결과로 나갈 수 있다.

**동시 도착은 선점 층이 받는다.** 주문 생성이 이미 쓰는 모양을 결제 시작과 주문 취소에도 그대로 적용한다.

- 진 쪽은 서버 오류가 아니라 **"같은 요청이 처리 중"을 뜻하는 전용 응답**을 받는다. 클라이언트가 그것과 진짜 장애를 구분할 수 있다.
- **DB 유일 제약은 안전망으로 남는다.** 선점 저장소가 죽었을 때 물러날 자리이며, 그때는 저장소 규칙대로 충돌을 정상 흐름에서 잡지 않는다.
- **선점 성공 뒤에 `(회원, 키)` 조회로 순차 재요청을 흡수한다.** 선점이 만료된 뒤 온 정당한 재요청이 새 자원을 만들지 않게 한다.
- **주문 취소는 주문 도메인에 이미 있는 선점 port를 쓰고, 결제 시작은 결제 쪽에 같은 성질의 port를 하나 둔다.** 결제가 주문의 port를 주입받으면 이번에 세운 경계가 깨진다.

검토했으나 채택하지 않은 안.

- **유일 제약 위반을 정상 흐름에서 잡아 재조회로 흡수한다** — 겉으로 보이는 동작은 같지만 "충돌은 안전망에 맡겨 드러낸다"는 저장소 규칙에 예외를 뚫어야 하고, 주문 생성과 또 다른 모양이 된다.
- **주문 취소에만 선점을 둔다** — 트랜잭션 무게 차이는 실재하지만, 커밋 전이라 진 쪽에게 성공으로 답할 수 없으므로 취소 쪽 답도 "처리 중"이 된다. 그러면 결제 시작과 형태가 같아져 가를 이유가 사라진다.
- **선점 port를 공용 자리로 올린다** — 쓰는 데가 둘뿐인데 어느 도메인 것도 아닌 층을 만들면 이번에 걷어내기로 한 것과 같은 문제가 된다.

## Consequences

- **프론트와 합의가 필요한 계약 변경이다.** 프론트는 취소 요청마다 고유값을 만들고 재시도할 때는 같은 값을 다시 보내야 한다. 주문 생성에서 이미 하는 일과 같다. 헤더를 보내지 않던 기존 호출은 깨진다.
- 부분환불이 들어와도 계약을 다시 바꾸지 않는다. 요청 단위로 구분되는 값이 이미 들어오므로 품목과 수량이 같은 두 요청도 갈린다.
- 세 경로(주문 생성·결제 시작·주문 취소)가 같은 모양이 된다. 계약을 대칭으로 맞춰 놓고 동시 도착에서만 한쪽이 서버 오류를 내는 비대칭이 사라진다.
- **진 쪽이 받는 것은 "앞서 만든 것"이 아니라 "처리 중"이다.** 앞 요청이 커밋에 성공할지 아직 모르는 시점이라 성공으로 답할 수 없다. 앞서 만든 것이 돌아오는 것은 그 뒤 같은 키로 다시 왔을 때다. **낙관 락 경합의 진 쪽을 취소 성공으로 답하는 것과 이 자리는 다르다** — 그쪽은 주문 취소와 환불 의도가 이미 커밋된 뒤라 회원이 잃는 것이 없지만, 이쪽은 커밋 전이다.
- 선점 저장소 의존이 결제·취소 경로에 는다. 해제를 빠뜨리면 만료될 때까지 같은 키가 막힌다.
- port 인터페이스가 도메인마다 하나씩 생겨 모양이 겹친다. 이 중복을 감수한다.
