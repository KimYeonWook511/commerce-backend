# Spec Constitution

이 문서는 spec-harness 워크플로(명세 확정 → 변환·검증 → 실행)를 관통하는
**불가침 원칙**을 정의한다. 일반 컨벤션(포맷·스타일·절차)과 달리, 여기 적힌 것은 양보하지 않는다 —
spec·plan·구현이 이 원칙과 충돌하면 **원칙이 아니라 그 산출물을 고친다.**

이 헌법은 두 가지로 구성된다.
- **직접 수록 원칙**: 독립 문서로 떼기엔 작지만 반드시 지켜야 하는 단편 규칙(예: 위험영역 불가침).
- **참조 규약**: 이미 독립 문서로 존재하는 규약을 "불가침"으로 격상해 가리킨다. 내용은 복사하지
  않는다 — 각 문서가 단일 출처이며, 그 변경 이력은 해당 문서의 git history가 추적한다.

---

## Core Principles

### I. 위험영역 불가침 (Risk Floor)

다음 네 영역은 **고위험 결정 영역**이다. 이 영역에 닿는 사항이 spec에서 확정되지 않았다면,
agent는 합리적 기본값으로 메우거나 추측으로 진행하지 않는다.

- **결제·정산** — 금액 계산, 결제 흐름, 환불, 정산 시점.
- **인증·인가** — 신원 확인, 권한 검사, 토큰·세션 수명.
- **데이터 모델·식별 규칙** — 엔티티 정의, 식별·유일성, Aggregate 경계, cross-aggregate 참조.
- **상태 전이(lifecycle)** — 엔티티 상태의 전이 조건, 허용/불가 전이, 종료 상태.

**강제 규칙** (이 영역이 미확정일 때):

1. **기본값 금지.** "표준 관행이니까"로 메우지 않는다. 다른 영역에서 허용되는 합리적 기본값
   채우기가 이 영역에서는 금지된다.
2. **마커 강제.** 미확정 사항은 반드시 `[NEEDS CLARIFICATION: 질문]`으로 남긴다.
3. **Clarify에서 면제 대상.** 이 마커들은 Clarify의 질문 수 한도(≤5)와 deferral(미룸) 대상에서
   **제외된다.** 다른 모호함이 5개를 채워도, 위험영역 마커는 항상 질문된다 — 우선순위에 밀려
   미뤄지지 않는다.
4. **확정 전 진행 금지.** 위험영역 마커가 남아 있는 한 Scenarios(4) 단계로 넘어가지 않는다.
   사용자가 확정해야만 해소된다.

**근거**: 결제·인증·데이터 모델·상태 전이는 잘못된 가정이 그대로 구현되면 데이터 정합성·보안·
금전 사고로 직결된다. 일반 모호함은 잘못 가정해도 재작업으로 끝나지만, 이 영역은 재작업으로
끝나지 않는다. 그래서 "묻지 않고 가정"의 자유를 이 영역에서만 박탈한다.

> 참고: 이 원칙은 *명세 단계의 게이트*다. "구현 시 이 영역을 어떻게 배치·구조화하는가"는
> 아래 참조 규약(특히 `package-structure-conventions.md`)이 다룬다. 둘은 층위가 다르며 보완 관계다.

## 참조 규약 (이들도 불가침)

아래 문서의 규칙은 일반 컨벤션이 아니라 **불가침 원칙**으로 취급한다. 위반하면 스타일 문제가
아니라 설계가 틀린 것이다. 내용은 각 문서가 단일 출처이며, 여기서는 복사하지 않고 가리킨다.

- **`package-structure-conventions.md`** — 4계층 레이어 의존 방향(`presentation → application →
  domain ← infrastructure`), Aggregate 경계, tx 경계(@Transactional은 service만), 엔티티 생성·
  상태 전이 규칙. ArchUnit으로 강제된다.
- **`exception-strategy.md`** — 도메인 예외 / 기술 예외 구분, 경계에서의 예외 변환 규칙.
- **`optimistic-lock-design.md`** — 낙관 락(@Version) 충돌의 tx 경계 밖 처리, 조건부 UPDATE로 금전 정합성을 지키는 동시성 설계.
- **`persistence-conventions.md`** — 영속성 계층 규약.
- **`test-code-conventions.md`** — 테스트 작성 규약.

새 규약을 불가침으로 올리거나 기존 항목을 격하하려면 이 목록을 수정한다(아래 Governance).

## Governance

- **우선순위**: 이 헌법은 다른 모든 관행·편의·기본값에 우선한다. 충돌 시 헌법을 따른다.
- **각 단계의 준수**:
  - **Clarify(3)**: 시작 시 이 헌법을 로드한다. 위험영역 미확정은 quota·deferral 면제로 강제 질문한다.
  - **Design(5)**: 설계 작성 시 헌법 위반이 없는지 확인한다. 위반이 있으면 정당화하거나 설계를 고친다.
  - **Analyze(7)**: 헌법 위반은 자동으로 CRITICAL로 분류한다. 헌법을 희석해 통과시키지 않는다.
- **개정**: 이 헌법의 변경은 PR로 한다. 무엇이 왜 언제 바뀌었는지는 git history가 추적한다
  (별도 버전 번호를 두지 않는다 — 단일 리포 내부 규율 문서이며 git이 곧 이력이다).
- **참조 규약의 진실**: 참조된 규약 문서의 내용이 바뀌어도 이 헌법은 그대로다. 그 변경의 이력은
  해당 문서의 git history가 가진다. 이 헌법이 추적하는 것은 "무엇을 불가침으로 삼는가"라는
  결정이지, 그 문서들의 내용 자체가 아니다.
