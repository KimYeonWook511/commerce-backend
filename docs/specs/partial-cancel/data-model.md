# 데이터 모델: partial-cancel

> 개념 모델 — 무엇이 존재하고 어떻게 식별·전이되는가. 물리 스키마는 `db-schema.md`가 다룬다.

---

## aggregate 경계

```
Order (루트)              Payment (루트)        Refund (루트)
 ├─ OrderItem                    ▲                   │
 │   └─ 취소 품목 내역           └── paymentId ───────┘
 └─ ...
        │
        └──── refundId (루트 식별자) ──────────────────▲
```

**환불은 결제의 구성원이 아니라 독립 루트다.** 결제를 식별자로 참조하고 자기 전이 메서드와 자기 낙관 락을 갖는다. 이 spec이 그렇게 만드는 것이 아니라 이미 그렇고, **취소 품목 내역이 환불을 가리키는 것이 규칙에 맞는 근거가 바로 이것이다** — 루트 식별자이기 때문이다.

**두 경계 사이는 루트 식별자와 값으로만 오간다.** 주문이 계산한 취소 값어치를 결제에 넘기고, 결제가 만든 환불의 식별자를 주문이 받아 내역에 적는다. 결제가 주문 품목을 읽거나 주문이 환불의 상태를 읽는 경로를 만들지 않는다.

### 취소 품목 내역을 주문 쪽에 두는 이유

- 그 행이 갖는 주문 품목 식별자는 **루트가 아니라 Order 내부 엔티티의 식별자**다. 결제 쪽에 두면 다른 aggregate를 루트 식별자로 참조한다는 결정과 어긋나고, 그런 참조가 이 저장소에 없다.
- 같은 키·다른 내용을 품목·수량 조합으로 대조해야 하는데(FR-009), 결제 쪽에 두면 **환불이 주문의 언어로 판정**하게 된다. 주문 쪽에 두면 그 판정이 Order 안에서 닫힌다.
- 값어치 대조(`Σ(단가 × 내역 수량) == 이번 환불액`)에 필요한 단가가 주문 품목에 있다. 결제 쪽에 두면 단가를 복제하거나 주문을 읽어야 한다.
- 용어가 맞아떨어진다 — 취소는 주문에 가하는 행위이고 환불은 돈이 돌아가는 것인데, **돈에는 품목이 없다.**

**"환불 한 건 단위로 묶인다"는 그대로다.** 그룹핑 키가 환불 식별자인 것도, 담는 값(환불 식별자·주문 품목 식별자·수량)도 바뀌지 않는다. 바뀐 것은 어느 aggregate의 구성요소인가뿐이다.

## 엔티티

### 주문 품목 (OrderItem) — 변경

| 속성 | 설명 |
| --- | --- |
| 상품 식별자 | 기존 |
| 주문수량 | 기존. 바뀌지 않는다 |
| 단가 | 기존. **주문 시점 사본**이라 상품 판매가가 바뀌어도 환불액이 달라지지 않는다 |
| **취소수량** | **신설.** 지금까지 취소된 수량의 누계 |

**파생값 — 저장하지 않는다**

- 잔여수량 = `주문수량 − 취소수량`
- 이 품목의 취소 값어치 = `단가 × 취소 요청 수량`

**불변식** (이 엔티티가 스스로 지킨다)

- 취소수량은 0 이상 주문수량 이하다.
- 취소수량은 오르기만 한다. 내려가지 않는다 — 취소를 되돌리지 않기 때문이다.
- 한 번에 올리는 수량은 1 이상이다.

### 취소 품목 내역 — 신설

| 속성 | 설명 |
| --- | --- |
| 주문 품목 식별자 | 어느 품목을 취소했나 (same-aggregate 참조) |
| 환불 식별자 | 그 취소로 열린 환불 (cross-aggregate 루트 참조) |
| 수량 | 그 요청에서 몇 개 취소했나 |

**유일성**: 환불 하나 안에서 주문 품목 하나당 한 줄. 한 요청에 같은 품목이 여러 줄로 오는 것을 거부하므로(FR-010) 이 유일성이 성립한다.

**생성 관문**: 이름 있는 정적 팩토리 하나로만 만들고 그 안에서 필수값과 수량 하한을 지킨다. 이 저장소가 엔티티 생성 불변식을 한 관문에 모으는 것을 관례로 삼는다.

**불변식**

- `Σ(한 주문 품목의 내역 수량) == 그 주문 품목의 취소수량`. 취소수량과 내역은 **같은 자리에서 함께** 움직여야 갈라지지 않는다.
- 수량은 1 이상이다.

### 주문 (Order) — 전이 조건 변경

상태값은 그대로다(`INIT` · `PAID` · `CANCELED`). 바뀌는 것은 **결제완료에서 취소로 가는 조건**이다.

| 전이 | 조건 |
| --- | --- |
| `INIT` → `CANCELED` | 기존 그대로. 결제 전 취소(사용자 직접·배치 만료) |
| `PAID` → `CANCELED` | **모든 품목의 잔여수량이 0이 될 때만.** 하나라도 남으면 `PAID` 유지 |
| `CANCELED` → 무엇이든 | 없음. 종착이다 |

**총 주문 금액을 깎지 않는다.** 그것은 주문 시점 금액의 사본이고 결제 금액이 그 값에서 나왔다. 취소로 줄이면 결제 금액과의 대조가 조용히 깨진다. 남은 값어치가 필요하면 `Σ(단가 × 잔여수량)`으로 계산한다.

### 환불 (Refund) — 변경 없음

이 작업이 환불의 속성도 상태 전이도 바꾸지 않는다. 취소 품목 내역이 환불을 가리킬 뿐이다.

## 도메인 책임 배치

잔여수량은 저장하지 않고 상태에서 파생되므로, **그 값을 계산하는 자리와 그 값으로 판정하는 자리가 갈리면 안 된다.** 흐름이나 트랜잭션 서비스가 `주문수량 − 취소수량`을 직접 계산해 비교하는 순간 도메인 규칙이 밖으로 샌다.

| 규칙 | 자리 |
| --- | --- |
| 잔여수량 계산 | 주문 품목 |
| 취소수량이 주문수량을 넘지 않는다 · 내려가지 않는다 · 수량이 1 이상 | 주문 품목 (전이 메서드 가드) |
| 요청 품목이 이 주문의 것인가 | 주문 |
| 한 줄이라도 초과하면 전부 거부 (FR-003) | 주문 |
| 품목 목록 생략 = 잔여 전부 (FR-002) | 주문 |
| 모든 잔여 0 판정과 상태 전이 (FR-005) | 주문 |
| 이번 취소의 값어치 계산 | 주문 |
| 같은 키 재요청의 품목·수량 대조 (FR-009) | 주문 |
| 확정된 줄이 하나도 없으면 거절 (FR-016) | 주문 |
| 취소 내역 생성 불변식(수량 1 이상·식별자 필수) | 취소 품목 내역의 생성 관문 |
| 금액 한도 판정 | 결제 (기존 그대로) |
| 잠그기 · 불러오기 · 위임 · 저장 · 결제사 호출 | 응용 계층 |

### 전부 거부는 롤백에 기대지 않는다

주문의 진입 메서드가 **두 번 훑는다** — 먼저 모든 줄을 검증하고, 통과한 뒤에야 반영한다. 트랜잭션 롤백이 결과적으로 같은 것을 보장하지만 그것은 인프라이고 FR-003은 도메인 규칙이다. aggregate 안에서 성립시켜야 단위 테스트로 잡힌다.

### 상태 전이를 밖으로 열지 않는다

"주문을 취소 상태로 만든다"는 메서드를 공개하지 않는다. 열어 두면 잔여수량이 남았는데도 밖에서 전이시킬 수 있어 FR-005가 강제되지 않는다. 품목을 취소하는 메서드 안에서 모든 잔여가 0인지 스스로 묻고 전이한다.

### 결제 전 취소와 결제완료 취소를 다른 관문으로 가른다

지금은 한 메서드가 상태만 보고 바로 전이한다. 부분취소가 들어오면 **상태는 더 이상 취소 가능 여부의 충분조건이 아니다** — 결제완료이면서 일부만 남은 주문이 정상 상태이기 때문이다. 두 전이를 한 이름에 몰면 성격이 다른 규칙이 한 가드를 공유해, 어느 쪽 규칙인지 읽어서 알 수 없게 된다.

- 기존 취소 메서드는 **결제 전 전용**으로 좁힌다. 호출처가 셋인데(사용자 직접 취소·배치 만료·**결제완료 취소**) 앞의 둘만 결제 전이고 셋째는 이 작업이 새 관문으로 옮길 대상이다. **그래서 좁히는 것과 옮기는 것을 같은 자리에서 해야 한다** — 먼저 좁히면 아직 옮기지 않은 결제완료 경로가 그 자리에서 깨진다.
- 결제완료 취소는 새 관문이 받는다.

## 취소 접수의 호출 순서

내역이 환불 식별자를 가지려면 환불이 먼저 저장돼야 하고, 환불을 열려면 금액이 먼저 필요하다. 그 순환을 **검증·계산과 반영을 가르는 것**으로 끊는다.

```
⓪ 그 키의 환불이 이미 있으면 주문이 그 내역과 요청 줄을 대조한다
     같으면 앞 결과를 돌려주고 여기서 끝낸다 (아래 어느 것도 하지 않는다)
     다르면 거부한다
        │
① 주문이 검증하고 계산한다 (상태를 바꾸지 않고, 주문 상태를 보지도 않는다)
     요청 줄들이 이 주문의 것인가 · 잔여수량을 넘지 않는가
     목록이 비었으면 **잔여가 남은 품목만 골라** 그 잔여수량으로 채운다
     확정된 줄이 하나도 없으면 여기서 거절한다
     → 확정된 줄 목록과 이번 취소 값어치를 돌려준다
        │
② 결제가 환불을 연다
     주문이 계산한 값어치를 받아 금액 한도를 판정하고 환불을 만든다 → 저장해 식별자를 얻는다
        │
③ 주문이 반영한다
     확정된 줄대로 취소수량을 올리고 내역을 남긴다 (환불 식별자를 적는다)
     모든 잔여가 0이면 상태를 전이한다
```

**대조 관문**은 앞 결과를 돌려줄지 거부할지를 가른다.

- **받는 것**: 환불 식별자와 요청 줄 목록.
- **답하는 것**: 같은가 다른가.
- **판정**: 그 환불 식별자를 가진 내역을 모아 요청 줄과 품목 식별자로 짝짓고, **짝이 없거나 줄 수가 다르거나 수량이 다르면 다르다고 답한다.** 순서는 따지지 않는다.
- **요청 줄이 비어 있으면 대조하지 않고 같다고 답한다**(FR-009).
- **저장된 내역이 하나도 없는데 요청 줄이 있으면 다르다고 답한다.** 이 작업 이전에 만들어진 환불에는 내역이 없어(`db-schema.md`, 되메움 없음) 그 환불이 무엇을 취소했는지 알 수 없다. 알 수 없는 것을 같다고 판정하지 않는다. 옛 클라이언트의 정당한 재시도는 품목 목록을 싣지 않아 바로 위 면제로 재생되므로 막히지 않는다.

**두 호출로 갈려도 판정은 여전히 aggregate 안에 있다.** ①이 규칙을 전부 적용하고, ③은 ①이 확정한 것을 그대로 반영한다. 취소수량과 내역이 ③ 한 곳에서만 움직여 갈라질 수 없다.

**금액을 결제에 인자로 넘기는 것은 규칙 누출이 아니다.** 갈림길은 "누가 계산했는가"다 — 응용 계층이 품목을 훑어 곱셈을 하면 누출이고, 주문이 계산한 값을 옮겨 심으면 누출이 아니다. 단가가 주문의 상태이므로 이 계산은 주문의 것이다. 승인 반려 환불이 금액을 받지 않는 것은 그 금액이 결제 상태에서 파생되기 때문이고, 여기 금액은 주문 상태에서 파생되므로 반대가 맞다.

## 동시성

### 주문 행 잠금이 수량 축을 지킨다

취소수량과 내역이 모두 Order aggregate 안에 있고, 그것을 바꾸는 모든 경로가 주문 행 잠금을 먼저 지난다. 두 요청은 직렬화되고, 진 쪽은 앞 요청이 커밋한 취소수량을 읽어 잔여 초과로 거절된다. 품목 행이나 결제 행에 추가 잠금이 필요 없다.

**규칙**: 취소수량을 바꾸는 모든 경로는 **주문 행 잠금을 먼저 잡는다.**

### 요청 단위 영속성 컨텍스트를 끈다

잠금 조회는 주문 행 하나만 잡고 품목은 그 뒤에 지연 로딩으로 읽는다(자식 행까지 잠금이 번지지 않게 일부러 그렇게 두었다). 그런데 이 저장소는 영속성 컨텍스트를 **요청 단위로** 열어 둔 상태이고(`open-in-view`가 기본값), 취소 흐름은 잠금을 잡기 **전에** 경로를 고르려고 같은 주문을 한 번 읽는다.

그러면 잠금 뒤에 읽는 품목이 **잠금 전에 만들어진 캐시**에서 올 수 있다. 지금 안전한 것은 그 앞선 조회가 품목을 함께 가져오지 않기 때문이지 순서를 지켜서가 아니다. 품목을 함께 가져오는 조회가 이미 저장소에 있고 같은 취소 흐름의 결제 전 경로가 그것을 쓰므로, 한 줄만 바뀌면 **낡은 취소수량을 읽고 총량을 넘긴다.** 컴파일도 단위 검증도 통과하고 경합에서만 틀린다.

**이 작업이 요청 단위 영속성 컨텍스트를 끈다.** 그러면 트랜잭션마다 컨텍스트가 새로 열려 앞선 조회가 캐시를 남기지 못하고, 잠금 뒤 읽기가 언제나 최신 커밋본을 본다. 순서를 규칙으로 지키는 대신 **구조로 불가능하게 만드는 것**이다.

깨질 자리를 지연 로딩 연관 셋으로 헤아린 결과와 이 설정을 어디에 두는지는 `adr.md`의 같은 결정에 있다.

### 결제 행 경합은 새로 실재한다

환불을 열면 결제 행의 돌려주기로 한 금액이 올라 버전이 바뀌고, 환불의 성공 확정도 같은 행을 갱신한다. 전액취소에서는 회원 취소가 주문당 한 번이라 겹칠 자리가 좁았으나, **부분취소는 같은 결제에 취소를 여러 번 건다.** 앞선 환불의 확정이 도는 중에 두 번째 부분취소가 들어오면 낙관 락 충돌이 나고, 회원 요청이므로 충돌이 그대로 올라가 거절된다(SCN-036). 반대로 부분취소가 먼저 커밋되면 앞선 확정이 밀려 그 환불이 미확정으로 남고 대사가 집는다(SCN-041).

**거절이 맞는 응답이고 재시도를 붙이지 않는다.** 언제 겹치는지는 결제사 응답 시간이 정하므로 우리가 통제할 수 없고, 거절된 요청은 취소수량·재고·환불 어느 것도 남기지 않아 회원이 다시 시도하면 된다. 이 저장소는 재시도 도입을 높은 경합이 실제로 관측될 때로 미뤄 두었는데, 이 경합은 회원이 한 화면에서 여러 품목을 고르면 **한 요청으로 오므로** 그 조건에 아직 닿지 않는다. 관측되면 그때 접수 트랜잭션에 재시도를 건다.

### 재고 복구는 취소한 품목만, 같은 정렬로

재고 복구가 상품 식별자 오름차순으로 도는 것은 재고 행 교착을 피하는 계약이다. 부분취소에서도 **취소한 품목만 골라 같은 정렬로** 돌아야 하고, 복구 수량은 주문수량이 아니라 취소 요청 수량이다.
