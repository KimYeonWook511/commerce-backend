# 구조: partial-cancel

> 어느 레이어에 무엇이 생기고 바뀌는가, 그리고 흐름의 순서·경계. 클래스 이름은 코드가 출처이며 여기서는 자리를 가리키는 데만 쓴다.

---

## 새 도메인도 새 레이어도 만들지 않는다

기존 order·payment 두 도메인 안에서 바뀐다. 레이어 배치는 `docs/package-structure-conventions.md`를 따른다.

| 레이어 | order | payment |
| --- | --- | --- |
| `presentation/http` | 취소 요청 본문 수신·형식 검증 | 없음 |
| `application/usecase` | 취소 흐름 조립(트랜잭션 없음), 커밋 후 결제사 호출 | 없음 |
| `application/service` | **취소 접수 단일 트랜잭션** | 없음 |
| `domain` | 잔여수량 판정·취소수량 반영·값어치 계산·상태 전이·취소 내역 | 없음 |
| `infrastructure/persistence` | 취소 내역 저장 | 없음 |

**payment 쪽은 이 작업이 바꾸지 않는다.** 환불을 여러 건 여는 것도, 금액을 밖에서 받는 것도 이미 된다. 같은 키 내용 대조를 주문으로 옮기지만 **결제 쪽의 기존 금액 대조를 걷어내지는 않는다** — 주문 쪽이 먼저 걸려 실질적으로 안 쓰이게 되나, 주문을 거치지 않는 경로가 나중에 생겼을 때의 안전망으로 남긴다.

**의존은 order → payment 한 방향뿐이다.** payment 쪽 후처리가 order를 읽는 경로를 만들지 않는다.

---

## 취소 접수 — 순서·경계

현행 구조를 유지하며 트랜잭션 안에서 하는 일이 늘어난다.

```
[presentation]
  중복 방지 키 헤더 검증 (없거나 비면 거부)
  요청 본문 형식 검증 (수량 1 이상, 같은 품목이 여러 줄이면 거부)
        │
[usecase] 트랜잭션 없음
  같은 주문·같은 키의 선점 표시를 잡는다 (못 잡으면 "처리 중"으로 답한다)
  주문 상태를 잠금 없이 조회해 경로를 고른다
    결제 전 → 기존 경로로 위임 (이번에 손대지 않는다)
    결제완료·취소 → 아래 트랜잭션 단위작업 호출
        │
[service] ──── 트랜잭션 시작 ──────────────────────────────
  ① 주문 행을 잠근다 (소유자 조건 포함, 단일 행)
  ② 환불 대상 결제를 찾는다
  ③ 그 결제·요청자·요청 키로 기존 환불을 찾는다
       있으면 → 그 환불과 주문 상태로 앞 결과를 만들어 반환하고 아래를 건너뛴다
                (주문이 그 환불의 내역과 요청 줄을 대조해 다르면 거부)
  ④ 주문이 결제완료인지 확인한다
  ⑤ 승인 결과가 확정되지 않은 결제가 걸렸으면 거부한다
  ⑥ 주문이 요청을 검증하고 계산한다 — 상태를 바꾸지 않는다
       요청 줄이 이 주문의 것인가 · 잔여수량을 넘지 않는가
       목록이 비었으면 잔여가 남은 품목만 골라 그 잔여수량으로 채운다
       확정된 줄이 하나도 없으면 여기서 거절한다
       → 확정된 줄 목록 + 이번 취소 값어치
  ⑦ 결제가 그 값어치로 환불을 연다 → 저장해 식별자를 얻는다
  ⑧ 주문이 반영한다 — 취소수량을 올리고 내역을 남기고, 모든 잔여가 0이면 전이한다
  ⑨ 재고 부분복구 (취소한 품목만, 상품 식별자 오름차순)
  ⑩ 저장
─────────────────── 커밋 ─────────────────────────────────
        │
[usecase] 커밋 후
  결제사 환불 호출 (best-effort)
  결과를 환불 진행 상태로 변환해 응답
  선점 표시를 푼다
```

### 지금과 달라지는 것

| 자리 | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| ③ 기존 환불 조회 | 트랜잭션 안에 있으나 **재생 판정은 usecase가 주문 상태로** 한다 | **이 자리에서 재생을 판정한다.** 주문이 결제완료로 남아 있어도 앞 결과를 돌려준다 |
| ⑥ 검증·계산 | 없음 (전액이라 계산할 것이 없다) | 신설 |
| ⑦ 환불 금액 | 결제에서 승인 금액을 꺼내 결제에 도로 넣는다 | **주문이 계산한 값어치**를 넣는다 |
| ⑧ 반영 | `주문을 취소한다` 한 번 | 취소수량·내역·전이 판정 |
| ⑨ 재고 | 주문 전량 복구 | **취소한 품목만, 취소 요청 수량만큼** |

### 재생 판정을 트랜잭션 안으로 옮기는 이유

지금은 usecase가 **주문 상태가 취소일 때만** 앞 결과를 찾는다. 전액취소에서는 "같은 키 재요청 = 이미 취소된 주문"이 성립했지만, **부분취소는 재요청 시점에 주문이 결제완료로 남아 있어** 그 경로를 타지 못한다. 그러면 취소를 다시 반영하려 들고, 환불은 기존 것이 반환되어 금액이 두 번 오르지 않지만 **재고 복구가 한 번 더 탄다.**

판정 기준을 "그 결제·요청자·요청 키의 환불이 이미 있는가"로 옮기고, 그 판정을 트랜잭션 안에서 한다. 선점 표시에는 유효 시간과 저장소 장애 시 물러나는 경로가 있어 앞단 검사만으로는 창이 닫히지 않는다.

### 경계에서 지키는 것

- **결제사 호출이 트랜잭션 밖이다.** ③에서 재생으로 걸린 경우에는 **호출하지 않는다** — 환불 재시도는 대사의 몫이고, 중복으로 부르면 한 사건에 두 주체가 겹쳐 상태 전이가 충돌한다.
- **재고 복구가 묶음의 맨 뒤다.** 재고 행 잠금 보유 시간을 줄이기 위한 기존 결정이며, 부분취소에서도 유지한다.
- **취소수량과 내역은 ⑧ 한 곳에서만 움직인다.** 갈라질 자리를 만들지 않는다.

## 요청 단위 영속성 컨텍스트를 끈다

주문 행 잠금 조회는 **그 행 하나만** 잡고 품목은 뒤에 지연 로딩으로 읽는다(자식 행까지 잠금이 번지지 않게 일부러 그렇게 두었다). 그런데 이 저장소는 영속성 컨텍스트를 **요청 단위로** 열어 두었고, 위 흐름의 `[usecase]` 단계가 경로를 고르려고 잠금 **전에** 같은 주문을 읽는다.

그래서 잠금 뒤에 읽는 품목이 **잠금 전에 만들어진 캐시**에서 올 수 있다. 지금 안전한 것은 그 앞선 조회가 품목을 함께 가져오지 않기 때문이지 순서를 지켜서가 아니다 — 품목을 함께 가져오는 조회가 이미 있고 같은 취소 흐름의 결제 전 경로가 그것을 쓴다. 한 줄만 바뀌면 낡은 취소수량으로 총량을 넘긴다.

**이 작업이 그 설정을 끈다.** 트랜잭션마다 컨텍스트가 새로 열려 앞선 조회가 캐시를 남기지 못한다. 순서를 규칙으로 지키는 대신 **구조로 불가능하게 만든다.**

깨질 자리를 지연 로딩 연관 셋으로 헤아렸고 어느 것도 걸리지 않는다. 그 대조와 검증이 이것을 확인하지 못하는 이유는 `adr.md`의 같은 결정에 있다.

## 도메인이 받는 입력

주문 도메인의 관문은 요청 DTO를 받지 않는다 — 받으면 도메인이 응용 계층을 참조하게 되어 의존 방향이 뒤집힌다. `(주문 품목 식별자, 수량)` 쌍의 목록을 order 도메인의 작은 값 타입으로 받는다.

같은 품목이 여러 줄인 것을 거부하는 규칙(FR-010)은 **요청 경계 한 곳에만** 둔다. 도메인도 목록을 받으므로 검출할 수 있으나, 양쪽에 두면 어느 쪽이 먼저 걸리느냐에 따라 응답이 갈린다.

## 무엇을 만들지 않나

- **주문 상세 조회 API** — 범위 밖이다.
- **두 축(수량·금액)의 대조 장치** — 두 aggregate를 넘어 읽어야 해서 의존 방향을 깬다. 이 작업 이후 취소를 지난 결제에서는 두 값이 일치하며(근거와 예외는 `spec.md`), 그 일치는 코드가 강제하는 불변식이 아니다.
- **결제 행 경합의 재시도** — 정상 경합이고 거절이 맞는 응답이다. 거절된 요청은 아무 상태도 남기지 않아 회원이 다시 시도하면 된다.
- **취소 요청을 담는 새 aggregate 루트** — 요청 단위 속성(요청 키·시각)이 이미 환불에 있어 담을 것이 없다.
