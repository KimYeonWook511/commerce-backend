# API 계약: partial-cancel

> 이 작업이 바꾸는 계약만 적는다. 루트 `docs/api-spec.md`가 현재 상태의 정본이며,
> Root Sync 단계가 여기 적힌 것을 그쪽에 반영한다.

---

## 바뀌는 것 한눈에

| 대상 | 변경 |
| --- | --- |
| `POST /orders/{orderId}/cancel` | **요청 본문 신설** (품목 목록). 주소·헤더·응답 형식은 그대로 |
| 응답 필드 | 없음 — `refundedAmount`·`remainingAmount`가 이미 있고 뜻도 유지한다 |
| 실패 응답 | 오류 셋 추가 |

**새 엔드포인트를 열지 않는다.** 잔여 전부 취소도 결국 부분취소의 특수한 경우이며, 주소를 나누면 잔여수량 검증·재고 복구·상태 전이·중복 방지가 두 벌이 되어 한쪽만 고치는 실수가 나기 쉽다.

---

## `POST /orders/{orderId}/cancel`

### 요청

- Path: `orderId`
- Header: `Idempotency-Key` — 필수, 64자 이하 (기존 그대로)
- **Body: 선택.** 없거나 빈 객체여도 된다.

```json
{
  "items": [
    { "orderItemId": 12, "quantity": 2 },
    { "orderItemId": 13, "quantity": 1 }
  ]
}
```

| 필드 | 규칙 |
| --- | --- |
| `items` | 선택. **없거나 빈 배열이면 아직 남은 품목만 골라 그 잔여수량 전부**를 취소한다. 이미 전부 취소된 품목은 대상에 들지 않는다 |
| `items[].orderItemId` | 필수. 그 주문에 속한 주문 품목 식별자 |
| `items[].quantity` | 필수. 1 이상. 그 품목의 잔여수량 이하 |

**금액을 받지 않는다.** 재고 복구가 품목 단위라 금액만으로는 무엇을 얼마나 복구할지 정할 수 없고, 부수적으로 클라이언트가 취소 금액을 부풀리는 경로가 막힌다.

**같은 `orderItemId`가 두 줄 이상 오면 거부한다.** 합치지 않는다 — 취소는 되돌릴 수 없으므로 모호한 의도를 서버가 해석해 실행하지 않는다.

### 응답

형식이 바뀌지 않는다. 두 금액의 뜻도 그대로다.

```json
{
  "code": "SUCCESS",
  "message": "OK",
  "data": {
    "orderId": 1,
    "status": "PAID",
    "refundStatus": "IN_PROGRESS",
    "refundedAmount": 10000,
    "remainingAmount": 40000
  }
}
```

| 필드 | 부분취소에서의 값 |
| --- | --- |
| `status` | **잔여수량이 남아 있으면 `PAID` 그대로.** 모든 품목이 0이 될 때만 `CANCELED` |
| `refundedAmount` | **이번 요청으로 취소한 품목의 값어치** — `Σ(주문 시점 단가 × 취소 요청 수량)` |
| `remainingAmount` | 계약이 정한 정의 유지 — `승인 금액 − 돌려주기로 한 금액` |

`remainingAmount`가 **금액 축**이고 취소 가능 여부 판정은 **수량 축**이라 서로 다른 값이지만, 회원이 취소할 수 있는 결제에서는 두 값이 일치한다(근거는 `spec.md`의 데이터 모델 절).

### 실패

기존 실패 응답은 그대로 두고 셋을 더한다.

| 상황 | 응답 | 비고 |
| --- | --- | --- |
| 어느 품목이든 잔여수량 초과 | `409` 취소 수량 초과 | **요청 전체가 거부**되고 아무 상태도 바뀌지 않는다 |
| 그 주문에 없는 `orderItemId` | `400` 잘못된 요청 | 남의 주문 품목인지 없는 품목인지 구분해 알려주지 않는다 |
| 같은 `orderItemId`가 여러 줄 | `400` 잘못된 요청 | |
| `quantity`가 1 미만 | `400` 잘못된 요청 | 입력 검증에서 걸린다 |
| 취소할 잔여가 하나도 없음 | `409` 취소 불가 | 검증·계산 관문이 확정된 줄을 하나도 못 만든 경우. 이미 취소된 주문은 그 앞의 상태 확인에서 걸린다 |
| 앞선 환불의 확정과 겹침 | `409` 동시 요청 충돌(공통) | 결제 행 낙관 락 충돌이 번역 없이 전파된다. 아무 상태도 바뀌지 않으며 다시 시도하면 된다 |

기존 실패는 그대로다 — 남의 주문·없는 주문은 같은 응답, 취소 불가 상태는 거부, 승인 결과를 모르는 결제가 걸리면 거부, 같은 키에 내용이 다르면 거부, 같은 키가 처리 중이면 재시도 권고.

**결제 행 경합과 같은 키 처리 중은 둘 다 409이지만 다른 실패다.** 앞엣것은 서로 다른 요청이 같은 결제 행을 다툰 것이고, 뒤엣것은 같은 요청이 아직 처리 중인 것이다. 앞엣것에 주문 도메인 코드를 새로 붙이지 않는다 — 번역은 안쪽이 그 예외에 따라 다르게 처리해야 할 때만 하고, 이 경로는 그대로 올려보내는 것이 맞다.

**요청 줄이 비어 있으면 내용을 대조하지 않는다.** 그 키의 환불이 있다는 사실만으로 앞 결과를 돌려준다 — 보낸 목록이 없으니 비교할 내용도 없다.

**같은 키에 내용이 다른 것을 가르는 기준이 바뀐다.** 지금은 금액과 사유를 대조하는데, 부분취소에서는 금액이 같아도 품목 조합이 다를 수 있다(1만원짜리 2개와 2만원짜리 1개). **품목 식별자와 수량의 조합**으로 대조하며, 목록의 순서는 따지지 않는다.

### 이미 취소된 주문에 다시 요청이 오면

기존 동작을 유지한다 — 같은 요청 키로 만들어진 환불이 있으면 그 결과를 그대로 돌려주고, 없으면 취소 불가로 거부한다. 부분취소는 여러 번 나눠 취소하다 마지막에 종착하므로 그 순간의 재시도가 지금보다 잦아진다.

## 오류 코드

새로 더하는 것은 하나다. 나머지 둘은 기존 잘못된 요청으로 접는다.

| 코드 | 범주 | 언제 |
| --- | --- | --- |
| 취소 수량 초과 | 충돌(409) | 어느 품목이든 잔여수량을 넘는 수량을 요청했다 |

**없는 품목 식별자와 같은 품목 중복을 별도 코드로 두지 않는 이유**: 둘 다 클라이언트가 요청을 잘못 만든 것이고, 회원이 할 수 있는 일이 "요청을 고쳐 다시 보낸다"로 같다. 잔여수량 초과는 다르다 — 요청 자체는 올바르고 그 사이 다른 요청이 먼저 취소했을 수 있어, 회원이 현재 잔여를 다시 확인해야 한다.

정확한 코드 문자열과 메시지는 구현 시 기존 체계(`ORDER-4xx-N`)를 따라 붙인다.

---

## 범위 밖

- **주문 상세 조회 API** — 클라이언트가 `orderItemId`를 얻을 경로가 지금 없다. 이 작업은 취소 계약만 열고, 그 경로는 별도 작업으로 뺀다. 그때까지 이 API는 품목 식별자를 이미 아는 호출자만 부분취소를 쓸 수 있고, 모르는 호출자는 품목 목록을 생략해 잔여 전부 취소를 쓴다.
