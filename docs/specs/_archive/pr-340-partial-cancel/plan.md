# 총괄 설계서: partial-cancel

> 무엇을 어떤 접근으로 만들 것인가, 그리고 몇 번에 나눠 통합·검증할 것인가.
> 관점별 상세는 `architecture.md`·`data-model.md`·`db-schema.md`·`api-spec.md`·`aggregate.yaml`이 다룬다.

---

## Summary

결제완료 주문에서 품목과 수량을 지정해 일부만 취소할 수 있게 한다. 주문 품목에 취소수량을 더해 잔여수량을 계산하고, 취소 한 번이 어느 품목 몇 개였는지를 주문 쪽에 남긴다. 모든 품목의 잔여가 0이 될 때에만 주문이 취소 상태로 간다.

**핵심 접근**: 부분취소를 별도 기능으로 만들지 않는다. 잔여 전부 취소도 부분취소의 특수한 경우이므로 같은 주소·같은 경로를 지나며, 품목 목록을 생략하면 잔여 전부로 채워 넣는다.

---

## 이 작업에서 달라지는 기술 맥락

스택 고정값은 규칙 문서를 따르고, 여기서는 이번에 달라지는 것만 적는다.

- **새 의존성 없음.** 결제사 어댑터가 이미 부분 금액 취소를 지원한다.
- **새 마이그레이션 하나** — 주문 품목에 컬럼 하나, 새 테이블 하나.
- **설정 하나** — 요청 단위 영속성 컨텍스트를 끈다(`open-in-view: false`). 저장소 전역 설정이라 이 작업의 범위를 넘지만, 수량 축 방어를 규칙이 아니라 구조로 세우기 위해 함께 넣는다.
- **새 오류 코드 하나** — 잔여수량 초과(409). 없는 품목 식별자·같은 품목 중복은 기존 잘못된 요청으로 접는다.

## 원칙 점검

| 항목 | 결과 |
| --- | --- |
| 위험영역 미확정 마커 | **0개.** 잔액 두 축·취소 내역 소속·재생 판정 기준이 모두 확정됐다 |
| 레이어 의존 방향 | 지킴. order → payment 한 방향이며, 취소 내역이 환불을 루트 식별자로만 가리킨다 |
| 트랜잭션 경계 | 지킴. 결제사 호출이 트랜잭션 밖이고, 재생으로 걸린 요청은 부르지 않는다 |
| `@Transactional` 위치 | 지킴. 트랜잭션 단위작업은 service, 조립은 usecase |
| 낙관 락 처리 | 지킴. 결제 행 경합은 트랜잭션 밖에서 받아 거절로 답한다 |
| 예외 처리 | 지킴. 무결성 위반을 정상 흐름에서 잡지 않고, 취소수량 상한을 도메인이 지킨다 |
| 시나리오 충족 | 42개 전부 이 설계로 확인 가능 |
| 설계가 드러낸 시나리오 | 6개 보강 — 결제 행 경합 양쪽(SCN-036·SCN-041), 결제완료 상태의 재생(SCN-037), 잔여 0 섞인 취소(SCN-038), 한도와 값어치 일치(SCN-039), 잔여 없는 주문의 목록 생략(SCN-040) |

### 이 작업이 택하지 않은 더 강한 안

**주문 품목을 잠금 조회로 다시 읽지 않는다.** 잠금 뒤 품목을 오름차순 잠금 조회로 읽으면 읽기 정합이 더 확실해지지만, 자식 행까지 잠금이 번지지 않게 한 기존 판단과 결이 다르다. 대신 **요청 단위 영속성 컨텍스트를 꺼서** 캐시 오염 자체를 없앴다. 규칙 문서 일곱을 대조했으나 이 선택이 어기는 대목은 없다.

## 구조 결정

| 결정 | 내용 |
| --- | --- |
| 취소 내역의 소속 | **order aggregate.** 주문 품목의 자식이며 환불을 루트 식별자로 가리킨다 |
| 잔여수량 판정 | **주문 도메인.** 품목 하나의 불변식은 품목이, 여러 품목에 걸친 판정은 주문이 |
| 상태 전이 | **공개하지 않는다.** 품목 취소 관문 안에서 스스로 판정해 전이한다 |
| 결제 전 취소와의 분리 | 기존 취소 메서드를 결제 전 전용으로 좁히고 결제완료용 관문을 새로 둔다 |
| 환불 금액 | **주문이 계산해** 결제에 넘긴다. 결제의 금액 인자 시그니처는 그대로 |
| 호출 순서 | 검증·계산(상태 불변) → 환불 저장 → 반영. 내역이 환불 식별자를 가져야 하는 순환을 이렇게 끊는다 |
| 재생 판정 | **환불 존재 여부**로 하고 트랜잭션 안에서 한다 |
| 동시성 | 주문 행 잠금이 수량 축을 지킨다. 품목·결제 행에 추가 잠금 없음 |
| 읽기 정합 | 요청 단위 영속성 컨텍스트를 꺼서 잠금 앞 조회의 캐시가 남지 않게 한다 |
| 결제 행 경합 | 거절로 답하고 재시도를 붙이지 않는다. 거절된 요청은 아무 상태도 남기지 않는다 |

### Root Sync에서 루트로 옮길 것

루트 상태 문서(`api-spec.md`·`architecture.md`·`db-schema.md`)와 ADR 말고 **하나가 더 있다.**

- **`docs/optimistic-lock-design.md`** — 요청 단위 영속성 컨텍스트를 끄면 "잠금 뒤 읽기는 언제나 최신 커밋본"이 저장소 전역에 성립한다. 그 문서가 동시성 설계의 단일 출처이고 같은 급의 전제를 이미 담고 있으므로, 이 전제를 그 문서에 더한다.
- **규칙 문서라 harness의 동기화 유예 대상이 아니다.** 유예는 위 상태 문서 셋만 덮는다. 방침을 바꾸는 결정은 ADR로 남기고 그 후속으로 규칙 문서를 갱신하는 것이 이 저장소의 규율이고, 여기서는 그 후속이 이 항목이다.
- 그 문서의 충돌 정책 표에서 전파 경로만 "도메인 예외가 끝단 핸들러로"라고 읽히는 칸이 있는데, 본문 두 곳은 "변환 없이"라고 적어 서로 어긋난다. 이번 작업이 그 전파 경로를 계약으로 확정하므로 그 칸도 함께 바로잡는다.

## Phase 구성

**phase 하나로 간다 — `1-main`.**

나눌 근거가 없다. 이 작업의 통합 지점은 "품목·수량으로 부분취소가 된다" 하나이고, 그 앞에 따로 검증할 가치가 있는 덩어리가 없다.

- **스키마만 먼저 넣는 phase를 두지 않는다.** 컬럼과 테이블이 생겨도 쓰는 코드가 없으면 검증할 것이 없고, 되메움도 없어 중간 확인 가치가 없다.
- **도메인만 먼저 만드는 phase를 두지 않는다.** 잔여수량 판정과 취소수량 반영은 접수 흐름과 함께여야 의미가 서고, 따로 두면 사용처 없는 코드가 한동안 남는다.
- 앞이 서야 뒤가 서는 강한 선후 의존도 없다 — 스키마·도메인·흐름·API가 한 기능의 앞뒤이지 서로를 기다리는 관계가 아니다.

**이 phase 끝에 검증되는 것**: 결제완료 주문의 품목·수량 부분취소가 접수·거부·재시도·동시 요청에서 모두 뜻대로 동작하고, 건드리지 않기로 한 경로(결제 전 취소·보상·전액취소·대사)가 그대로 통과한다.

step은 다섯이다.

1. `disable-open-in-view` — 설정을 끄고 전체 회귀로 영향을 확인한다
2. `order-item-cancelled-quantity` — 마이그레이션과 주문 도메인
3. `replay-by-existing-refund` — 재생 판정을 환불 존재로 옮긴다 (전액취소 동작 유지)
4. `partial-cancel-flow` — 요청 본문·접수 흐름·재고 부분복구·응답·실패. 여기서 부분취소가 동작한다
5. `partial-cancel-concurrency` — 실제 경합 재현

**1을 맨 앞에 둔 것은** 뒤 step들이 세울 수량 축 방어가 그 설정에 기대기 때문이다. **3을 4보다 앞에 둔 것은** 재생 판정 이동이 전액취소 상태에서도 동작 변화 없이 검증되고, 그 위에 4가 서면 부분취소 멱등이 자연히 성립하기 때문이다.
