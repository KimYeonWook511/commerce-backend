# API 계약: payment-refund-model

> 변경 2개. 형식은 루트 `docs/api-spec.md`를 따른다.
> **본문 형식은 어느 쪽도 바꾸지 않는다** — 품목·수량을 받는 형태는 부분환불 요청을 다루는 별도 작업에서
> 정한다. 다만 **두 엔드포인트에 요청 헤더가 하나씩 늘어난다.**
>
> **둘 다 프론트와 합의가 필요하다.**

## `POST /payments` (경로 변경 · 요청 헤더 추가)

지금 경로는 `POST /payments/reserve`다. 설명은 그대로다 — 결제창을 띄우기 전에 결제사에 보낼 키를
발급받는다. **응답 형태도 그대로다.**

### 바뀌는 점

| | 지금 | 이후 |
| --- | --- | --- |
| 경로 | `POST /payments/reserve` | **`POST /payments`** |
| 요청 헤더 | 없음 | **`Idempotency-Key` 필수** |
| 요청 본문 | | **변경 없음** |
| 응답 | | **변경 없음** |
| 실패 응답 | | **셋 추가** — 요청 형식 검증(멱등키 헤더 누락) · **409 "같은 요청이 처리 중"** · **같은 멱등키에 내용이 다른 요청** |

### 요청

```
POST /payments
Idempotency-Key: <클라이언트가 만든 고유값>
```

- 로그인 인증이 필요합니다.
- **주문은 요청한 회원의 것이어야 한다.** 남의 주문 번호를 실으면 **주문을 찾을 수 없다는 응답**으로
  거절한다 — 그 주문이 있는지조차 드러내지 않는다.
- **클라이언트가 결제 시작 요청마다 고유값을 만든다.**
- **같은 요청을 다시 보낼 때는 같은 값을 다시 쓴다.** 그래야 결제창이 한 번만 열린다.
- 값이 없으면 요청을 거절한다.

**유일 범위는 그 회원의 결제들이다** — 주문 생성과 같다. 결제는 한 주문에 여러 번 시도할 수 있으므로
결제로 묶을 수 없고, 주문으로 묶으면 재시도가 막힌다.

- **다른 회원이 같은 값을 보내도 서로 영향이 없다.** 기존 결제를 찾을 때 회원과 함께 좁히므로 남의
  결제가 돌아오지 않는다. 값의 형식을 제한하지 않으므로 문자열이 겹치는 것 자체는 막지 않는다.
- **길이는 최대 64자다.** 넘으면 요청 형식 검증으로 거절한다. UUID(36자)·SHA-256 hex(64자)가 들어가는
  크기이며, **주문 취소 쪽도 같다.** 서버가 잘라 담지 않는 것이 중요하다 — 앞 64자가 같고 뒤만 다른 두
  요청이 하나로 접히면 **앞 요청의 결제창 값이 뒤 요청에 돌아가고**, 회원이 그 창에서 인증해 엉뚱한
  주문이 결제된다. 바로 아래 "같은 값에 다른 주문을 실어 보내면 거절한다"가 막으려는 것과 같은 사고다.
- **같은 값에 다른 주문·다른 금액을 실어 보내면 거절한다.** 그대로 돌려주면 앞 주문의 결제창 값이
  나가고, 회원이 그 창에서 인증해 **엉뚱한 주문이 결제된다.** 실패 응답도 안 나가므로 아무도 모른다.

### 같은 값이 동시에 닿으면

**앞 요청이 아직 끝나지 않았다면 진 쪽은 409를 받는다** — 주문 생성이 쓰는 것과 같은 뜻의 전용 응답이다.
주문 취소도 같다.

```
409  "같은 요청이 이미 처리 중입니다. 잠시 후 다시 시도해 주세요."
```

- **서버 오류가 아니다.** 클라이언트가 진짜 장애와 구분할 수 있어야 한다. 구분되지 않으면 이 경로의
  오류를 통째로 무시하게 되고, 결제가 실제로 안 되는 상황도 함께 묻힌다.
- **멱등키가 서로 달라도 이 응답이 나갈 수 있다.** 같은 주문에 결제 시작이 동시에 오면 **한 주문에
  활성 결제 하나**라는 제약이 한쪽을 막는데, 그때도 같은 값을 준다 — 회원이 할 일이 "잠시 후 다시"로
  같기 때문이다. **앞 결제가 아직 승인을 부르지 않았으면 순차로 온 두 번째가 그것을 죽이고 정상
  성공하므로**, 그 경우 이 응답은 동시에 닿았을 때만 나온다.
- **앞 결제가 승인을 부른 뒤면 순차로 와도 거절한다.** 다만 그때 나가는 것은 이 응답이 아니라 아래
  **"승인 결과를 모를 때의 응답"**이다. 회원이 할 일이 "잠시 후 다시 눌러 보기"가 아니라 **"결과를
  기다리기"**여서다 — 잠시 뒤 다시 눌러도 같은 거절이 오고, 승인이 성공하면 그 주문은 결제완료가 되어
  새 결제 자체가 필요 없어진다.
- **앞서 만든 것이 돌아오지는 않는다.** 앞 요청이 커밋에 성공할지 아직 모르기 때문이다. 그것이 돌아오는
  것은 **잠시 뒤 같은 키로 다시 물었을 때**다.
- **이 응답을 받고 무엇을 할지는 클라이언트가 정한다.** 잠시 뒤 같은 키로 다시 묻든, 회원에게 안내하든
  된다. 서버는 구분할 수 있게 답하는 데까지다.

**따닥은 이 응답에 기대지 말고 버튼을 막아 해결한다.** 서버 쪽 방어가 겨냥하는 것은 **끊긴 연결 뒤의
재전송**이다 — 그때는 앞 요청의 성공 응답이 끊긴 연결로 사라져, 클라이언트가 받는 것이 이 응답 하나뿐이다.

### 왜 경로를 바꾸나

**"예약"이라는 개념이 이번에 사라진다.** 예약 테이블을 없애고 결제 행이 시도 원장이 되므로, 그대로 두면
없어진 개념의 이름만 경로에 남는다.

**하는 일이 자원 생성이다.** 결제 시도를 하나 만들고 그 정보를 돌려준다. 주문 생성이 이미 같은 성질을
자원 경로로 표현하고 있고, 멱등키 헤더와 유일 범위까지 둘이 대칭이 된다.

| | 주문 | 결제 |
| --- | --- | --- |
| 자원 생성 | `POST /orders` | **`POST /payments`** |
| 멱등키 | `Idempotency-Key` 필수 | **`Idempotency-Key` 필수** |
| 유일 범위 | 그 회원의 주문들 | **그 회원의 결제들** |
| 자원에 대한 행위 | `POST /orders/{orderId}/cancel` | `POST /payments/naverpay/approve` |

**지금 바꾸는 것이 가장 싸다.** 프론트는 지금도 더 옛 경로를 부르고 있어 서버와 어긋나 있고, 멱등키
헤더 때문에 어차피 고쳐야 한다. 지금 함께 바꾸면 **한 번만** 고치면 된다.

### 왜 필요한가

지금은 **한 주문에 살아 있는 결제가 하나**라는 것만 지킨다. 그래서 버튼을 두 번 누르거나 네트워크
재시도가 일어나면 **결제창이 두 번 열리고 앞 결제가 종결된다.** 회원 눈에는 앞 창이 갑자기 죽는 것으로
보이고, 우리 쪽에는 쓰이지 않는 결제 행이 쌓인다.

### 무엇을 새로 해야 하나

- 결제 시작 요청마다 고유값을 만들어 헤더에 싣는다.
- **재시도할 때는 같은 값을 다시 보낸다.** 값이 바뀌면 새 요청으로 처리되어 방지가 무의미해진다.
- 주문 취소가 쓰는 것과 **같은 헤더 이름·같은 생성기**를 쓴다. **다만 값을 화면이나 세션 단위로 붙들어
  두면 안 된다** — 다른 주문의 결제를 시작할 때 그 값이 다시 나가면 서버가 거절한다. 값을 새로 만드는
  단위는 **"이 주문을 결제하겠다"는 한 번의 의사**이고, 재시도는 그 안에서 같은 값을 다시 쓰는 것이다.
- **경로를 새 것으로 바꾼다.** 경로와 헤더가 한 벌로 나간다.

## `POST /orders/{orderId}/cancel` (요청 헤더 추가 · 응답 확장)

설명은 지금과 같다. 회원이 자기 주문을 취소하고, 결제 완료 주문이면 전액이 환불된다.

### 바뀌는 점

| | 지금 | 이후 |
| --- | --- | --- |
| 요청 헤더 | 없음 | **`Idempotency-Key` 필수** |
| 요청 본문 | 없음 | **변경 없음** |
| 응답 | 주문 번호·상태·환불 진행 상태 | **이번 환불액과 남은 취소 가능 금액 추가** |
| 실패 응답 | | **셋 추가** — 요청 형식 검증(멱등키 헤더 누락) · **409 "같은 요청이 처리 중"** · **같은 멱등키에 내용이 다른 요청**. 환불 관련 실패는 변경 없음 |

### 요청

```
POST /orders/{orderId}/cancel
Idempotency-Key: <클라이언트가 만든 고유값>
```

- 로그인 인증이 필요합니다.
- **자기 주문만 취소할 수 있다.** 남의 주문 번호를 실으면 **주문을 찾을 수 없다는 응답**으로 거절한다.
  기존 동작과 같고 이번에 바뀌지 않는다.
- **클라이언트가 취소 요청마다 고유값을 만든다.**
- **같은 요청을 다시 보낼 때는 같은 값을 다시 쓴다.** 그래야 환불이 한 번만 일어난다.
- 값이 없으면 요청을 거절한다.

**헤더 이름은 주문 생성과 같지만 유일 범위가 다르다.**

| | 주문 생성 | 주문 취소 |
| --- | --- | --- |
| 헤더 | `Idempotency-Key` | `Idempotency-Key` |
| 같은 값이 겹치면 안 되는 범위 | **그 회원의 주문들** | **그 결제에서 회원이 요청한 환불들** |
| 다른 주문에 같은 값을 써도 되나 | 안 된다 | **된다** — 각각 별개 요청으로 처리된다 |

취소 쪽 범위가 더 좁으므로 **주문 생성용 키 생성기를 그대로 써도 문제가 없다.** 반대는 성립하지 않는다.

**내부 제약에는 요청자가 함께 든다.** 프론트가 보내는 것은 회원 요청뿐이라 위 표에 드러나지 않지만,
승인 반려로 시스템이 만드는 환불이 같은 자리를 다투지 않도록 저장소 쪽 유일 범위는 결제·요청자·키 셋이다.

> **프론트와 합의가 필요한 계약 변경이다.** 새로 하는 일은 취소 요청마다 고유값을 만들어 보내고,
> 재시도할 때 같은 값을 다시 보내는 것이다.

### 응답

- `refundStatus`: 환불 진행 상태. `NONE`(결제 전 취소) / `COMPLETED` / `IN_PROGRESS` — **값은 지금과
  같다.** 다만 환불 상태가 다섯으로 늘어나므로 **무엇이 무엇으로 접히는지를 표로 고정한다.**

  | 환불 상태 | 응답 값 | 왜 |
  | --- | --- | --- |
  | (환불 없음 — 결제 전 취소) | `NONE` | 되돌릴 돈이 없다 |
  | `SUCCEEDED` | `COMPLETED` | 돈이 돌아갔다 |
  | `REQUESTED` · `IN_PROGRESS` · `UNKNOWN` | `IN_PROGRESS` | 돌아가는 중이다 |
  | `MANUAL_REVIEW` | `IN_PROGRESS` | 자동으로는 더 진행되지 않지만, 사람이 이어받아 결국 돌아간다. 회원에게 문제를 알려도 할 수 있는 일이 없고 문의만 는다 |

  값이 늘지 않으므로 **프론트가 받는 형태는 그대로다.**
- `refundedAmount`: **이번 요청으로 환불되는 금액.** 주문 총액이 아니며, 앞서 환불된 몫은 포함하지 않는다
  - **결제 행의 누적 환불액(`totalRefundedAmount`)과 다른 값이다.** 그쪽은 그 결제의 **모든** 환불
    합이고 이쪽은 **이번 건 하나**다. 이름을 갈라 둔 것은 그 값을 그대로 응답에 옮기는 실수를 막기
    위해서다 — 전액환불만 있는 지금은 두 값이 우연히 같아 드러나지 않고, **부분환불이 오는 순간
    틀린 값이 나간다.**
  - 이번에 만드는 환불 사건의 금액을 그대로 싣는다.
- `remainingAmount`: **앞으로 더 취소할 수 있는 금액.** 전액 환불되면 0
  - **`승인 금액 − 누적 환불액`이다.** 환불 한도와 **같은 축·같은 계산**이라, 이 값이 0이 아니면 그만큼
    더 취소할 수 있다는 뜻이다. 프론트가 "취소 가능 금액"으로 그대로 쓸 수 있다.
  - **"아직 안 돌아온 돈"이 아니다.** 결과를 모르는 환불도 **한도를 이미 잡고 있어** 여기서 빠진다 —
    10,000원 결제에 3,000원 환불을 요청한 직후라면 그 건이 아직 진행 중이어도 이 값은 7,000원이다.
    돈이 실제로 돌아갔는지는 `refundStatus`가 말한다.
  - **주문 금액이 아니라 승인 금액이 기준이다.** 둘이 다른 결제는 반려로 종결되므로 성공한 결제에서는
    두 값이 같지만, **한도를 재는 것이 승인 금액**이라 그쪽에 맞춘다. 기준이 갈리면 한도는 통과하는데
    응답이 0을 말하거나 그 반대가 된다.
  - **결제 전 취소는 0이다.** 승인 금액이 아직 없어 한도 자체가 없고, 그 주문은 이미 취소돼 더 취소할
    것도 없다.

```json
{
  "code": "SUCCESS",
  "message": "OK",
  "data": {
    "orderId": 1,
    "status": "CANCELED",
    "refundStatus": "COMPLETED",
    "refundedAmount": 10000,
    "remainingAmount": 0
  }
}
```

결제 전 주문을 취소하면 환불이 없으므로 `refundStatus`는 `NONE`, `refundedAmount`도 0이다.
`remainingAmount`도 0이다 — **승인 금액이 없어 한도가 없고**, 그 주문은 이미 취소돼 더 취소할 것도 없다.

**결제사를 부르지 못한 채 끝나도 `IN_PROGRESS`로 답한다.** 이 요청이 결제사를 부르기 직전 상태 전이에서
다른 주체(대사나 다른 요청)에게 밀리는 경우가 있는데, 그때는 **부르지 않고 그대로 응답한다.** 실패로
답하지 않는다 — 주문 취소와 환불 의도는 이미 커밋됐고, 밀렸다는 것은 **다른 쪽이 대신 보내고 있다**는
뜻이라 회원이 잃는 것이 없다. 결제사 호출이 실패했을 때도 같다.

**같은 주문에 같은 멱등키로 다시 요청하면** 새 환불이 생기지 않고 앞서 만든 사건의 결과가 그대로
응답된다. **다른 회원이 같은 키를 보내면** 그 사건이 돌아오지 않는다 — 찾는 범위가 그 요청이 가리키는
결제에 딸린 환불들이라 남의 결제는 아예 보지 않는다.

### 왜 지금 넣나

**응답 필드**: 이번 범위에서는 전액환불만 일어나므로 두 값은 항상 **결제 전액과 0**이다. 그래도 지금 넣는
이유는 **부분환불을 다루는 작업이 응답 구조를 건드리지 않아도 되게** 하기 위해서다.

**요청 헤더**: 서버가 결제 식별자에서 값을 파생하면 같은 결제에서 늘 같은 값이 나온다. 그러면 실패로 끝난 뒤
재환불이 유일 제약에 막히고, 같은 결제에 회원 환불과 승인 반려 환불이 함께 생길 때 값이 수렴해 한쪽이
거부된다. **부분환불에서는 "같은 품목 같은 수량" 요청이 중복인지 진짜 두 번인지 서버가 구분할 수도 없다.**

지금 도입하면 부분환불이 올 때 **계약을 다시 바꾸지 않아도 된다.** 프론트 합의가 걸린 변경이라 두 번 하면
두 배로 든다.

### 환불 관련 실패 응답을 바꾸지 않는 이유

한도를 넘는 요청은 이번 범위에서 나지 않는다. 전액환불만 하므로 한 번 환불된 주문은 다시 요청할 수
없고, 결과를 모르는 환불이 떠 있는 경우는 기존 응답이 이미 막는다. **쓰이지 않는 실패 코드를 미리
계약에 두지 않는다.**

**예외는 둘이다** — 요청 형식 검증(멱등키 헤더 누락)과 **"같은 요청이 처리 중"**. 환불 처리에
들어가기 전 단계다.

### 응답 시간에 대해

**커밋 뒤 같은 요청 안에서 결제사를 부르고 결과를 응답에 담는다.** 그래서 대개 회원이 "환불 완료"를
바로 본다. 네이버페이 명세는 취소 timeout을 최소 60초로 두라고 하지만, **회원이 기다리는 자리에서는
그보다 짧게 끊고 "처리 중"으로 답한다**(`spec.md` FR-035).

결제사 호출을 요청 흐름에서 **완전히 떼어내는 것**은 후속 과제다 — 그러면 항상 "접수됨"이 되어 화면
설계가 함께 바뀐다.

---

## 승인 결과를 모를 때의 응답 (계약 유지 — 문서에 없던 것을 적는다)

**계약은 바뀌지 않는다.** 지금 동작이 코드에만 있어서, 승인 경로를 새 모델로 옮기며 조용히 사라지지
않도록 적어 둔다.

**승인을 부른 뒤 결과가 정해지지 않은 결제가 그 주문에 있으면** 회원에게 이렇게 답한다. 승인을 호출하고
아직 응답을 기다리는 중인 경우와, 응답을 못 받아 **결과 불명**으로 남은 경우 둘 다다 — 회원에게는 같은
상황이고 할 일도 같아서 가르지 않는다. 내부 상태를 응답으로 드러내지 않는 쪽이기도 하다.

```
409  "결제 결과 확인 중입니다. 잠시 후 주문 내역에서 확인해 주세요."
```

**결제완료도 결제실패도 아니다.** 둘 다 위험하기 때문이다.

| 보여주면 | 실제로 그 반대였을 때 |
| --- | --- |
| 결제완료 | 회원이 물건을 기다리는데 **주문이 안 잡혀 있다** |
| 결제실패 | 회원이 다시 결제한다 → **돈이 두 번 나간다** |

같은 이유로 **그 주문에 새 결제 시도를 막는다.** 안 막으면 회원이 다시 눌러 이중결제가 된다.

### 그 뒤 어떻게 풀리나

대사가 이력을 조회해 확정한다. **결과 불명에는 대사 유예가 없어** 다음 대사 주기에 바로 집히고, 다시 집는
간격이 회차마다 벌어지되 상한이 있다.

- 승인이 성공했으면 → 결제 성공, **주문 결제완료.** 회원이 주문 내역에서 확인한다
- 그 사이 주문이 취소됐으면 → **승인 반려**로 가서 돈을 돌려준다

**이번 작업이 바꾸는 것은 하나다.** 지금은 일정 시간이 지나면 자동 확인이 멈춰 **아무도 안 보면 그 주문이
영구히 막히는데**, 그것을 멈추지 않게 한다. 회원이 보는 응답은 그대로다.

> **회원을 결제사 응답에 묶어두지 않는 방향**은 이번 범위가 아니다. 결과 불명일 때 실패로 응답해 재결제를
> 유도하고 이미 나간 돈은 나중에 정리하는 설계가 가능하지만, **일시적으로 돈이 두 번 나가는 것을 감수**
> 해야 하고 화면 설계도 함께 바뀐다. 후속 과제로 남긴다.

## 바뀌지 않는 것

- 결제 시작 API의 **응답 본문** — 결제사에 보낼 키를 발급하는 주체가 예약 행에서 결제 행으로 바뀌지만,
  프론트가 받는 값은 같다. **경로와 요청 헤더는 위에서 바뀐다.**
- 승인 관련 엔드포인트 — 밖에서 보이는 동작이 같아야 한다.
  - 다만 **승인 요청이 그 회원의 것인지 확인하는 근거가 예약에서 결제 행으로 옮겨진다.** 밖에서 보이는
    동작은 같다 — 남의 결제 키로는 찾을 수 없고, 그 번호가 있는지조차 드러나지 않는다.
