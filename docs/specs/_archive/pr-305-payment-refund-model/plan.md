## Summary

결제와 환불을 **테이블 셋으로 가른다.** 결제 예약 테이블을 없애 결제 행이 시도 원장이 되게 하고,
환불을 **독립 aggregate로 두되** "환불 총액이 결제 승인액을 넘지 않는다"는 불변식은 **환불을 만드는
트랜잭션이 지키고 판정은 결제가 한다.** 그 위에서 결제사 환불 연동의 일곱 가지 결함을 고친다.

```
tbl_payment          결제 시도 원장 (예약 흡수, 활성 슬롯으로 이중결제 차단)
tbl_refund           환불 사건 — 독립 aggregate. 결제를 식별자로 참조한다(FK 없음)
                     판정과 한도 계산이 기대는 금액의 정본

tbl_pg_call_log      결제사 호출 기록 — aggregate 밖. 승인·환불 호출을 한 곳에 쌓고
                     응답 원본을 담는다. 쌓기만 하고 판정에 쓰지 않는다
```

## 이 작업에서 달라지는 기술 맥락

스택 고정값은 규칙 문서를 따르고, 여기서는 **이번에 새로 도입하거나 바꾸는 것**만 적는다.

| 무엇 | 지금 | 이후 |
| --- | --- | --- |
| 결제 행 생성 시점 | 결제사 호출 뒤 | **결제창을 띄우기 전** |
| 결제사 결제 번호 | 필수 | **비어 있을 수 있음**(승인 뒤에 채워짐) |
| 이중결제 차단 | 예약 슬롯 + 승인 슬롯 두 테이블 | **결제 행의 활성 슬롯 하나** |
| 환불 표현 | 결제와 한 테이블, 종류 값으로 구분 | **별도 테이블, 결제 1:N** |
| 환불 중복 차단 | 4열 유일 제약 | **(결제, 요청자, 환불 요청 멱등키) 유일 제약** |
| 낙관 락 | 결제 행에만, 행이 바뀔 때만 버전 증가 | **환불도 자기 버전을 갖는다.** 환불을 만들 때만 결제 버전도 함께 오른다 ← 새 규칙 |
| 한도의 기준 금액 | 없음(결제 금액을 씀) | **결제사가 승인한 금액을 따로 담는다** |
| 결제사 결과 어휘 | 넷 | **넷.** 다시 시도할 수 있는 실패와 없는 실패를 가른다 |
| 결제사 호출 기록 | 환불만, 뽑아낸 값만 | **승인·환불 한 곳에, 응답 원본까지. 둘 다의 밖** |
| 환불 생성 | "찾거나 만드는" 별도 tx 서비스 | **결제의 도메인 메서드** |
| 취소 요청 계약 | 멱등키 없음 | **헤더로 받는다** ← 프론트 합의 필요 |
| 결제 시작 계약 | 멱등키 없음, 경로가 "예약"을 가리킴 | **자원 생성 경로 + 멱등키 헤더** ← 프론트 합의 필요 |
| 결제사 패키지 | 결제사가 최상위, 그 안에 네 계층 | **레이어가 바깥, 결제사는 `infrastructure/pg/` 안** |
| 결제사에 나가는 인터페이스 | 결제사 이름이 붙은 것 + 함수형 콜백 | **결제사 이름 없는 것 하나** |
| 결과 회수 | 일정 시간 뒤 멈춤 | **멈추지 않는다. 간격은 회차마다 벌어지되 상한이 있다** |
| 대사의 환불 집행 | 환불 행이 있으면 집행 | **그대로.** 대신 부당한 행이 아예 생기지 않게 만든다 |

## 원칙 점검 (GATE)

### 위험영역

`spec.md`에 미확정 마커가 **0개**다. 결제·데이터 모델·상태 전이가 모두 확정됐고, 명세가 답을 주지
않는 두 가지(멱등키 보관 기간·이력 순서 보장)는 **모른다는 것을 전제로 삼는 설계**로 처리했다 —
전자는 **이력 조회로 먼저 회수하고 거기서 정해지지 않는 것을 같은 키 재전송이 받으며**, 후자는 순서에
의존하지 않는 판정을 쓴다.

### 규칙 문서 대조

**이번 설계의 실제 산출물과 대조한 것만 적는다.** 적용 대상이 없는 규칙은 넣지 않는다.

### 트랜잭션 경계 점검

**결제사 호출이 데이터베이스 트랜잭션 안에서 일어나지 않는다.** 기존 규칙 그대로다 — 환불 의도를
주문 취소와 한 트랜잭션에서 커밋한 뒤, 커밋 밖에서 결제사를 부른다.

**환불 생성을 결제의 도메인 메서드로 옮긴다.** 이전 안은 자기 트랜잭션 선언을 가진 별도 서비스를 두고
호출자 트랜잭션에 합류시키는 것이었는데, 그것은 **혼자 불러도 되는 것처럼 생긴 문**이다. 트랜잭션 없이
부르면 먼저 커밋되어 주문이 취소되지 않은 채 환불 의도만 남고, 대사가 그것을 집행한다. 실제로 일어나
최근에 고친 결함이고, 낙관 락 규칙 문서가 경고하는 형태가 정확히 그것이다.

도메인 메서드로 옮기면 **환불을 만들려면 결제를 로드해야 하고 주문도 함께 다뤄야 한다는 사실이 코드에
드러나** 혼자 부를 수 있는 문이 사라진다.

### 한 트랜잭션에 넷이 묶이는 것 — 예외 기록

주문 취소 트랜잭션에 들어오는 aggregate는 **넷**이다 — 주문, 결제, **환불**, 그리고 **재고**.
환불이 독립 aggregate가 되면서 결제와 한 덩어리로 셀 수 없게 됐다. 적게 세면 실제 경계보다 좁게
말하는 것이다.

**주문·결제·환불을 묶는 이유**는 나누면 **주문은 취소됐는데 환불 의도가 아직 없는 순간**이 생기기
때문이다. 돈이 걸린 자리에 그 틈을 만드는 위험이 더 크다. 결제가 함께 드는 것은 **그 행의 누적 환불액이
한도를 지키는 자리**여서다.

**재고가 함께 들어오는 것은 이번에 만든 것이 아니라 이미 그런 상태다.** 주문 취소가 재고를 되돌리는데,
그 서비스는 자기 트랜잭션을 열 수 있는 모양이라 **혼자 불러도 커밋된다.**

| 무엇 | 왜 묶이나 | 이번에 바뀌나 |
| --- | --- | --- |
| 주문 + 결제 + 환불 | 나누면 돈이 걸린 틈이 생긴다 | **이번에 묶는다** |
| 재고 | 주문 취소가 재고를 되돌린다 | **안에 두되 묶음의 맨 뒤로 옮긴다** |

**재고를 안에 두는 것은 따져 보고 정한 것이다.** 돈 정합성이 요구하는 최소 집합에 재고는 들지 않지만,
밖으로 빼면 **"취소는 됐는데 재고가 안 돌아온" 상태**가 생기고 그것을 회수할 장치가 따로 필요해진다.
대신 **락 보유 시간을 줄이려고 묶음의 맨 뒤에 둔다.** 그 락 대기로 취소가 실패할 수 있다는 것은
감수하며, **그 실패를 다른 실패와 구분해 남겨** 경합이 실제로 문제가 되는지 보고 그때 다시 정한다.

그리고 이 경계는 **구조로 강제할 수 없으므로 검증으로 받는다.** 주문 취소가 롤백되면 환불 의도도 남지
않는다는 검증이 그것이다.

### 로깅 규칙에서 이번 작업에 걸리는 것

| 규칙 | 이번 작업에서 |
| --- | --- |
| 도메인 상태 전환은 INFO | **새 상태가 늘고 전이가 바뀐다.** 환불 REQUESTED·UNKNOWN 진입과 종결에 INFO |
| Infrastructure는 외부 호출 실패·retry를 남긴다 | 결제사 어댑터가 거절·재시도 가능 실패를 WARN |
| Controller·Domain은 로그 없음 | 판정이 도메인으로 오므로 그 자리에는 로그를 넣지 않는다 |
| 마스킹 | **응답 원본에 마스킹된 카드번호가 들어온다.** 그것을 로그로 옮기지 않는다 |

### 테스트 규칙에서 이번 작업에 걸리는 것

| 규칙 | 이번 작업에서 |
| --- | --- |
| **낙관 락 충돌은 winner를 단언하지 말고 불변식으로 검증한다** | 대사 둘이 같은 건을 집는 시나리오들이 여기 걸린다. "성공 전이는 정확히 1건" 같은 불변식으로 단언한다 |
| 동시성은 타이밍에 의존하지 않는다 | 창을 결정론적으로 만들고 결과는 불변식으로 받는다 |
| 새 테이블이 생기면 테스트 정리 순서를 갱신한다 | **환불과 호출 기록 테이블이 새로 생긴다.** 외래 키는 걸지 않으므로 정리 순서를 안 고치면 행이 쌓여 다음 테스트를 오염시킨다 |

### 시나리오 충족 점검

`scenarios.md`의 시나리오 전부가 이 설계로 확인 가능한지 대조했다. 확인할 수 없는 것은 없다.

**Analyze 1라운드 뒤 시나리오가 크게 늘었다.** 설계 판단이 바뀌면서 드러난 것들이다 — 결제사 응답을
접는 규칙, 트랜잭션 경계, 승인 금액, 호출 기록, 슬롯 종결 대상, 신원 확인, 결제 대사. 요구와 완료 기준이
빠짐없이 시나리오로 덮이는지는 기계로 대조한다.

### 복잡도·예외 기록

**환불을 독립 aggregate로 둔 것**은 불변식이 두 개체에 걸치는데도 그렇게 한 것이다. 경계가 실제로
일하는 것은 환불을 **만들 때**뿐이기 때문이며, 그 한 자리는 트랜잭션이 지킨다(ADR 50). 대가로 한도
판정에 조회가 늘지 않는다 — 승인 금액도 누적 환불액도 결제 행에 있어 결제를 로드하는 것으로 끝난다.

**환불 상태를 다섯으로 둔 것**은 결제와 대칭을 맞추기 위해서다. **재전송이 부를 준비 상태를 지나가지
않으므로**, 그 상태에 있다는 것만으로 **아직 안 나갔음이 확실하다.** 얻는 것은 같은 이름이 같은 뜻을
갖는 것과, 커밋은 됐는데 호출이 아예 안 일어난 건이 상태로 드러나는 것이다.

**결제사 호출 기록을 aggregate 밖에 둔 것**은 그것이 어떤 불변식에도 참여하지 않기 때문이다. 루트를 통해
저장하면 판정에 참여하지 않는 기록이 낙관 락 충돌을 일으킨다. **필요한 성질은 결제 쪽이 롤백돼도
"불렀다"는 사실이 남는 것**이라 별도 트랜잭션으로 커밋한다.

**응답 원본을 DB에 담는 것**은 조사 근거를 남기기 위해서다. 결제사마다 응답 모양이 다르고 실패 응답에는
명세의 응답 표에 없는 항목이 실려 온다. 대가로 카드번호·계좌번호가 함께 담기지만 **결제사가 이미 일부를
가린 값으로 보낸다.** 이 판단이 서는 조건은 **밖에서 이 원본을 읽는 진입점을 만들지 않는 것**이다.
**보관 기간과 접근 제한은 이번에 정하지 않는다** — 관련 제도·법령을 확인해야 정할 수 있는 후속 과제다.

**환불 첫 시도를 요청 흐름 안에서 하는 것**은 지금 동작을 유지하는 것이다. 대개 즉시 완료되어 회원이
"환불 완료"를 바로 본다. **회원이 기다리는 자리에서는 결제사가 요구하는 시간보다 짧게 끊고 "처리 중"으로
답한다.** **비동기로 완전히 떼어내는 것은 후속 과제로 남긴다** — 그러면 항상 "접수됨"이 되어 화면
설계가 함께 바뀌어야 한다.

## 구조 결정

### 무엇이 무엇을 강제하나

| 지켜야 할 것 | 무엇이 강제하나 |
| --- | --- |
| 한 주문에 활성 결제 하나 | 결제 행의 활성 슬롯 컬럼 유일 제약 |
| 같은 요청으로 환불이 두 번 생기지 않음 | 결제와 묶은 환불 요청 멱등키 유일 제약 |
| 환불 총액 ≤ 결제 승인액 | 결제의 도메인 메서드가 판정 + 결제 행 낙관 락이 동시 요청 차단 |
| 환불 상태를 바꿔도 한도 계산이 어긋나지 않음 | **한도가 상태와 무관한 금액 합이다.** 상태 변경은 결제를 건드리지 않는다 |
| 환불 의도와 주문 취소가 함께 커밋됨 | **환불을 만드는 자리가 그 트랜잭션 안이다.** 혼자 불러 먼저 커밋되는 문이 없다 |
| 정당하지 않은 환불이 아예 생기지 않음 | **환불이 만들어지는 자리가 정당한 조건과 같은 트랜잭션.** 대사는 행이 있으면 집행하고 다시 확인하지 않는다 |
| 결제사 호출이 트랜잭션 밖 | 단위작업 여섯 — 의도 커밋 → **부르기 직전 전이 커밋** → 호출 기록 → 호출(tx 밖) → 결과 반영 → 기록 채우기 |

### 결제사별 차이를 어디서 흡수하나

도메인이 아는 결제사 결과는 **넷**이다 — 됐다 / 모른다 / 다시 시도할 수 있는 실패 / 다시 시도할 수 없는
실패. 결제사별 확인 수단(이력 조회)은 어댑터 안에 가둔다. 지금 세
유스케이스에 흩어진 결제사 호출을 어댑터 구현체 하나로 모은다.

**그 어댑터가 결제사 전용 타입이 사는 유일한 자리다.** 지금은 결제사가 최상위 묶음이고 그 안에 네 계층이
들어가 있어, **주문 유스케이스까지 결제사 전용 인터페이스를 주입받는다.** 레이어를 바깥에 두고 결제사를
인프라 안에 넣으면 결제사를 더 붙일 때 **새로 만드는 것이 어댑터 하나로 줄어든다.**

**결제사 코드를 그 넷으로 접는 표도 어댑터가 갖는다.** 결제사를 더 붙일 때마다 그 결제사의 표를
만들며, 표가 틀리면 조용히 틀리므로 접는 규칙을 시나리오로 고정한다.

대사가 "언제 다시 물어볼지" 판단할 때 결제사 사정이 어댑터 밖으로 새지 않게 하는 것이 이 설계의
과제다 — 어댑터는 결과를 표준 형태로 돌려주고, 다시 물어볼 시점은 도메인 쪽 정책이 정한다.

## Phase 구성

**두 개로 나눈다.** 앞이 서야 뒤가 서는 선후 의존이 분명하고, 중간에 한 번 검증할 가치가 있다.

> **phase는 작업을 가르는 단위이지 배포 단위가 아니다.** 두 phase를 다 돈 뒤에 PR이 한 번 열리고,
> 그것이 유일한 머지 단위다. **phase 1만 원격에 나가는 상태는 없다.** 그래서 아래 순서를 정한 근거는
> "그 사이에 배포하면 무엇이 깨지나"가 아니라 **"그 step을 검증할 때 필요한 것이 갖춰져 있나"**다.

### 옛 것을 옆으로 치우고 빈 자리에서 짓는다

새 모델은 엔티티 필드가 통째로 바뀐다 — 결제 종류 값이 사라지고, 상태값이 달라지고, 실패 코드가 둘로
갈리고, 시각 컬럼이 새로 생긴다. **옛 엔티티를 그 자리에서 고치면 그것을 참조하는 119개가 한꺼번에
깨져**, 첫 step이 나머지 step의 일을 전부 삼켜야 빌드가 통과한다.

그래서 **지금 결제 도메인을 `payment/legacy/`로 통째로 옮기고 옛 테이블을 그대로 둔 채** 빈 자리에서
새로 짓는다. 경로를 하나씩 갈아끼우고, 마지막에 legacy와 옛 테이블을 한 번에 지운다.

```
step 1        legacy 로 이동 + 옛 테이블 유지        빌드·테스트가 그대로 통과한다
step 2~       새로 짓고 경로를 하나씩 갈아끼운다      매 step 마다 통과한다
phase 2 끝    legacy 와 옛 테이블을 지운다            지우기만 하는 step
```

**얻는 것**: step마다 빌드가 실제로 통과하고, 각 step이 작아지고, 되돌리기 쉽다. 그리고 **새 코드가
옛 이름에 끌려가지 않는다** — 빈 자리에서 시작하므로 `naming-map.md`가 정한 이름을 그대로 쓴다.

**대가**: 두 벌이 잠시 공존한다. 컨트롤러 경로·스케줄러·결제사 설정이 겹치지 않게 다뤄야 하고, 통합
테스트의 테이블 정리 순서가 그동안 길어진다.

그리고 **"코드베이스에 ~가 없다"를 검증하는 시나리오는 legacy가 사라져야 참이 된다.** 셋이 그렇다 —
결제사 전용 타입이 계층 밖에 없다, 옛 후처리 분기가 남지 않는다, 환불 의도를 혼자 만드는 문이 없다.
**앞 step에서는 새 코드 범위로만 확인하고, 코드베이스 전체 검증은 `remove-legacy` step이 한다.**
앞에서 아예 안 보면 새 코드가 규칙을 어겨도 마지막까지 드러나지 않으므로 양쪽에 둔다.

**병행 기간에 두 모델이 같은 주문을 다투지 않는다는 것은 가정이다.** 옛 테이블과 새 테이블이 각자
활성 슬롯 유일 제약을 갖고 **서로를 모르므로**, 같은 주문에 양쪽 경로로 결제가 서면 활성 결제가 둘
성립한다. 이 작업은 **운영 중인 결제·환불 데이터가 없다는 전제** 위에 서 있고(파괴적 마이그레이션의
근거와 같다), 그 전제가 이 경합도 함께 덮는다. **전제가 깨지면 두 경로를 동시에 열어 두는 구간 자체가
위험하므로**, 그때는 옛 진입점을 먼저 닫고 진행해야 한다.

### 1-model-and-approval

legacy를 격리하고, **새 도메인·스키마·결제사 경계를 세운 뒤 결제 시작과 승인 경로를 갈아끼운다.**
결제 쪽 배치 셋도 여기서 선다.

```
1  isolate-legacy-payment            옮기고 옛 테이블 이름을 비켜 준다. 동작은 안 바뀐다
2  new-domain-and-schema             엔티티 셋 · 새 테이블 셋 · 리포지토리
3  pg-boundary-and-history           나가는 인터페이스와 어댑터. 이력 판정 결함 셋을 고친다
4  payment-start-path                결제 시작. 경로와 멱등키 헤더가 바뀐다
5  approval-path                     승인 요청 · 확정. 주문과 결제를 함께 커밋한다
6  rejection-refund-and-limit        한도 판정 · 승인 반려. 되돌리는 환불이 여기서 붙는다
7  payment-reconcile-notify-expire   회수 · 통지 · 만료. legacy 스케줄러의 결제 실행만 끈다
```

**옛 테이블 이름을 첫 step에서 비켜 주는 이유**: 다음 step이 최종 이름으로 새 테이블을 만드는데 옛
테이블이 그 이름을 쥐고 있으면 **엔티티와 스키마가 어긋나 애플리케이션이 뜨지 않는다.**

**반려 환불이 승인 경로 바로 뒤에 붙는 이유**: **반려는 승인 경로의 결과 중 하나**라, 그것 없이는
승인 step이 온전히 검증되지 않는다. 승인이 났는데 받아들일 수 없는 경우를 만들어 놓고 되돌리는 쪽이
비어 있으면, 그 시나리오를 돌릴 수 없다.

**결제사 경계를 앞쪽에 두는 이유**: 승인 경로가 그것을 쓰기 때문이다. 그리고 이력 판정 결함이 승인
대사의 전제라, 그것을 고친 뒤에 대사를 세워야 무엇이 깨졌는지 가릴 수 있다.

**이 phase 끝에 검증되는 것**: 결제 시작부터 승인 확정·반려·대사까지가 새 모델 위에서 돌고, **밖에서
보이는 동작이 이전과 같다.** **결제사 전용 타입에 대한 의존이 인프라 밖으로 나가지 않는다** — 경로와
그것을 받는 진입점 이름에는 결제사 이름이 남는데, 그 경로는 결제사가 정하는 규격이라 우리가 고를 수
있는 것이 아니다.

### 2-refund-and-reconcile

환불을 세우고 **주문 취소에 이으며 결제사 환불 연동을 교정한다.** 그 뒤 legacy를 지우고 규칙 문서를
현재 코드와 맞춘다.

```
1  order-cancel-and-refund-dispatch    주문 취소 연결 · 환불 발송 · 발송 배치. legacy 환불 실행을 끈다
2  refund-reconcile-and-notify         회수 · 통지 · 이력 판정 · 초과 거절 세 갈래
3  remove-legacy                       legacy 와 옛 테이블을 지운다. 지우기만 한다
4  rule-docs-correction                규칙 문서 넷을 현재 코드와 맞춘다
```

**한도 판정과 승인 반려는 phase 1로 옮겼다.** 원래 이 phase의 첫 step이었는데, 그러면 **승인 경로가
서는 step과 되돌리는 환불이 붙는 step 사이에 phase 경계가 놓인다.** 승인 경로를 검증하려면 반려도
함께 있어야 하는데, 그것이 다음 phase에 있으면 **승인 step을 닫을 때 그 시나리오를 돌릴 수 없다.**
legacy로 대신할 수도 없다 — legacy 반려는 옛 테이블의 결제 행을 요구하고 새 경로의 결제는 거기 없다.

**환불을 실제로 보내는 것은 phase 2에 남긴다.** phase 1은 반려로 만들어진 **환불 행까지**만 책임지고,
발송·회수·통지는 뒤 phase가 세운다. 개발 순서가 그 모양이기 때문이다 — 결제가 도는 것을 먼저 확실히
하고, 정상 흐름을 완성한 뒤에 예외와 경계를 다듬는다. **이것까지 앞으로 당기면 phase 1이 결제와 환불을
통째로 지고 phase 2가 비어 버려, 나눈 의미가 없어진다.**

**이 phase 끝에 검증되는 것**: 한 결제에 환불이 여러 건 쌓이고, 한도가 동시 요청에서도 지켜지며,
이력 판정이 순서·페이지·취소 종류와 무관하게 같은 결과를 내고, 대사가 정당하지 않은 환불을 집행하지
않는다. **그리고 legacy가 흔적 없이 사라진다.**
