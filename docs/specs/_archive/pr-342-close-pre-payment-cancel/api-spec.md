# API Spec: close-pre-payment-cancel

> 이 spec이 바꾸는 계약만 적는다. 루트 `docs/api-spec.md`로의 승격은 Root Sync가 한다.

## `POST /orders/{orderId}/cancel`

주소·요청 헤더·요청 본문은 바뀌지 않는다. **어떤 주문을 받는지와 그 실패 응답이 바뀐다.**

### 바뀌는 것

| 항목 | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| 취소를 접수하는 주문 | 결제 전(`INIT`)과 결제완료(`PAID`) | **결제 전 주문을 거부한다.** 결제완료 주문은 그대로 접수하고, 취소로 종착한 주문은 지금처럼 상태로 미리 가르지 않고 환불 존재 여부로 멱등 재생을 판정한다 — **같은 요청 키의 재요청만** 앞선 결과를 받고, 다른 키로 오면 취소 불가로 거부된다 |
| 결제 전 주문 취소 | 재고만 복구하고 성공 응답. 품목 지정 불가 | **`409 ORDER-409-2`로 거부.** 주문 상태·재고·결제가 그대로 남는다 |
| 결제완료 주문 취소 | 전액·부분 취소, 환불, 멱등 재생 | 그대로 |
| 응답 필드 `refundStatus`의 `NONE` | 결제 전 취소에서 나갔다 | **응답 계약에서 뺀다.** 그 값을 만들던 자리가 결제 전 취소 관문뿐이고 그것이 사라져, 프로덕션에서 아무도 만들지 않는 값이 된다. 관문 제거에 딸린 정리라 별도 시나리오를 두지 않는다 — 유일한 생산자가 없어지므로 남겨 두면 컴파일이 잡는다 |
| 응답 필드 `remainingAmount`가 0 | 결제 전 취소는 승인 금액이 없어 0 | 결제완료 주문에서 잔여 취소 가능 금액이 0인 경우에만 0이 된다 |

### 결제 전 주문 취소 요청의 응답

```
HTTP 409
{
  "code": "ORDER-409-2",
  "message": "주문을 취소할 수 없습니다",
  "data": null
}
```

새 오류 코드를 두지 않는다. 결제완료 취소 관문의 상태 가드가 이미 이 코드를 던지고 있고, 결제 전
주문이 그 가드에 걸리기 때문이다 — 이미 취소된 주문, 취소할 잔여가 없는 주문과 같은 답이다.

**결제 전 주문에는 걸린 결제가 어떤 상태든 이 답 하나만 나간다.** 같은 관문 안에 승인 결과를 모르는
결제를 보고 "결제 확인 중이니 잠시 후 다시 시도하라"고 답하는 검사가 따로 있지만, 상태 판정이 그보다
앞이라 결제 전 주문은 거기 닿지 않는다 — 결제 전 주문에는 그 안내가 실현될 길이 없다.

### 요청이 지나는 순서

```
취소 멱등키 선점  →  결제완료 취소 관문 [ 소유 확인 조회(잠금)  →  멱등 재생 판정  →  취소 가능 판정 ]
```

**소유 확인이 판정보다 먼저다.** 남의 주문 번호나 없는 주문 번호를 실으면 취소 불가가 아니라
**`404 ORDER-404`(주문을 찾을 수 없습니다)**로 답한다. 주문 조회가 주문 식별자와 회원 식별자로 함께
좁히기 때문이며, 두 경우가 같은 조회로 수렴해 답이 갈릴 자리가 없다. 바뀌지 않는 기존 응답이다.

**멱등 재생 판정이 취소 가능 판정보다 먼저다.** 그래서 취소로 종착한 주문에 같은 요청 키로 다시
보내면 상태 판정에 닿기 전에 앞선 결과가 나간다. 다른 키로 오면 그 판정에 닿아 `409 ORDER-409-2`로
거부되고, 같은 키라도 요청한 품목·수량이 그 환불로 기록된 취소 내역과 다르면 앞선 결과가 아니라
`400 PAYMENT-400-23`(요청 키 충돌)로 거부된다. 셋 다 바뀌지 않는 기존 응답이다.

**소유·존재 확인이 잠금 조회 안에서 일어난다.** 그래서 남의 주문 번호나 없는 주문 번호를 실은 요청도
그 행 잠금을 짧게 잡았다가 아무것도 바꾸지 않고 롤백한다. 그 잠금을 얻지 못하고 대기가 끝나면 404나
409가 아니라 **`500`(잠금 획득 실패)**이 나간다 — 같은 행을 오래 쥐는 주체가 없어 실현 가능성이 낮다고
보아 별도 응답을 두지 않는다.

선점이 그 트랜잭션보다 앞서지만 선점 키가 **주문 식별자와 멱등키 조합**이라, 남의 주문 번호를 실은
요청이 그 주문의 정당한 취소와 부딪치지 않는다. 이 논증이 기대는 것은 멱등키가 유일하다는 것이 아니라
**밖에서 추측할 수 없다는 것**이다 — 진행 중인 남의 취소와 같은 키를 맞히면 아래의 "처리 중"이 나가
그 주문이 취소 처리 중임이 드러나지만, 공격자가 스스로 열 수 있는 창이 아니다.

다만 **같은 회원이 같은 멱등키로 동시에 두 번** 보내면 진 쪽이 `409 ORDER-409-3`(같은 취소 요청이 이미
처리 중)을 받아, 순차로 두 번 보냈을 때(둘 다 `409 ORDER-409-2`)와 답이 갈린다. 아무 상태도 바뀌지
않으므로 그 갈림을 받아들인다.

### 결제 전 주문은 어떻게 정리되나

회원이 취소할 수 없고, 만료 배치가 취소하고 재고를 되돌린다. 그동안 그 주문이 잡은 재고는 팔리지
않으며 **이 대기 시간을 회원이 줄일 방법은 없다.**

만료 배치는 활성 슬롯을 쥔 결제가 걸린 주문을 건너뛰므로, 결제가 슬롯을 놓아야 주문 만료가 시작된다.
그래서 대기 시간이 결제를 얼마나 시작했는지에 달린다 — 결제를 한 번도 시작하지 않았으면 주문 만료
기준 + 배치 주기이고, 결제창을 열었으면 그 결제가 만료된 뒤에야 시작된다. 자세한 값은 `spec.md`의
가정에 있다.

**결제를 반복해서 다시 시작하면 이 정리가 일어나지 않는다.** 새 결제 행이 생길 때마다 결제 만료 시계가
처음부터 다시 시작하기 때문이다. 이 spec이 만든 것은 아니지만 이 spec이 그것을 푸는 출구를 닫으므로,
그 경로는 issue #341이 따로 다룬다.

### 문서에서 지울 것

루트 `docs/api-spec.md`의 취소 절에서 아래 서술이 사라진다.

- "`INIT`(결제 전)과 `PAID`(결제 완료) 주문을 취소할 수 있습니다"
- "`INIT` 취소: 재고만 복구합니다(환불 없음). 품목을 지정할 수 없습니다"
- `refundStatus` 표의 "(환불 없음 — 결제 전 취소) → `NONE`" 행. 그 값 자체가 응답에서 빠지므로 표에서 지운다
- `remainingAmount` 설명의 "결제 전 취소는 승인 금액이 없어 0입니다"
