# Architecture: close-pre-payment-cancel

> 이 spec이 바꾸는 구조만 적는다. 루트 `docs/architecture.md`로의 승격은 Root Sync가 한다.

## 무엇이 바뀌나

주문 취소 경로에서 **결제 전 갈래가 사라진다.** 새로 생기는 자리는 없고 하나가 없어진다.

### 지금

```
POST /orders/{orderId}/cancel
  └ 취소 흐름 조립 (트랜잭션 없음)
      ├ 취소 멱등키 선점
      ├ 주문 조회 (주문 식별자 + 회원 식별자, 잠그지 않음)
      ├ 결제 전이면 ──→ 결제 전 취소 관문
      │                   ├ 주문 조회(품목 함께) → 결제 전 취소 전이
      │                   └ 재고 복구 (동기)
      └ 그 외면   ──→ 결제완료 취소 관문
                          ├ 주문 행 잠금 → 환불 재생 판정 → 취소 계획 → 환불 생성 → 취소 반영 → 재고 복구
                          └ 커밋 뒤 결제사 환불 발송

주문 만료 배치
  └ 만료 대상 조회 → 활성 슬롯을 쥔 결제가 걸린 주문 제외 → 만료 트랜잭션
                                                              ├ 결제 전 취소 전이
                                                              └ 재고 복구 이벤트 생성 (비동기)
```

### 바뀐 뒤

```
POST /orders/{orderId}/cancel
  └ 취소 흐름 조립 (트랜잭션 없음)
      ├ 취소 멱등키 선점
      └ 결제완료 취소 관문          ← 분기와 잠그지 않은 조회가 사라진다
          ├ 주문 행 잠금 (주문 식별자 + 회원 식별자)
          ├ 환불 재생 판정 → 있으면 앞 결과를 돌려준다
          ├ order.checkCancellable()   ← 이 관문에 있던 상태 가드가 도메인으로 옮겨온다
          │   └ 결제완료가 아니면 도메인 예외 ──→ 거부 (취소 불가)
          ├ 취소 계획 → 환불 생성 → 취소 반영 → 재고 복구
          └ 커밋 뒤 결제사 환불 발송

주문 만료 배치 (그대로)
```

**결제 전 취소 관문이 사라진다.** 만료 배치는 그 관문을 쓰지 않고 자기 만료 트랜잭션이 주문의
결제 전 취소 전이를 직접 부르므로, 이 제거는 만료 경로에 닿지 않는다.

## 책임 배치

| 자리 | 역할 | 이 spec에서 |
| --- | --- | --- |
| 취소 요청 진입점 | 요청 형식 검증, 흐름 위임 | 그대로 |
| 취소 흐름 조립 | 멱등 선점, 커밋 뒤 결제사 호출 | **경로 선택이 없어진다.** 상태로 가르던 분기와 그것을 위한 잠그지 않은 조회가 사라지고 결제완료 취소 관문으로 바로 보낸다. 소유 확인은 그 트랜잭션이 잠그며 하던 대로 한다 |
| 결제 전 취소 관문 (`CancelOrderService`) | 결제 전 취소 전이 + 동기 재고 복구 | **제거.** 취소 응답을 주문만으로 만드는 팩토리와 "환불 없음" 값도 함께 사라진다 |
| 결제완료 취소 관문 | 주문 행 잠금, 환불 재생 판정, 상태 확인, 취소 반영, 재고 복구 | **상태를 꺼내 비교하지 않고 `order.checkCancellable()`을 부른다.** 나머지는 그대로 |
| 만료 트랜잭션 | 결제 전 취소 전이 + 재고 복구 이벤트 | 그대로 |
| 주문 도메인 | 결제 전 취소 전이, 취소 계획·반영 | **취소 가능 판정(`checkCancellable`)을 갖는다** — 결제완료가 아니면 던진다. 결제완료 취소 관문에 있던 상태 가드가 여기로 옮겨온다. 전이 메서드는 그대로 — 만료 배치가 계속 쓴다 |

## 의존 변화

- 주문 계층이 재고 서비스에 거는 의존이 하나 줄어든다. 결제완료 취소 관문의 재고 복구는 그대로라
  의존 자체가 없어지지는 않는다.
- 새로 생기는 의존은 없다.

## 남는 것

취소된 주문에 승인이 도착했을 때 결제를 종결하고 환불을 여는 보상 경로는 **그대로 둔다.** 만료 배치와
승인 확정이 겹치는 극단 경합에서는 여전히 그 경로가 필요하다. 이 spec이 없애는 것은 그 경로가
정상 흐름에서 열리는 것이다.
