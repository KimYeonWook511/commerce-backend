# 인터뷰 기록 — 결제 재시작으로 만료 시계가 초기화되어 주문 재고가 풀리지 않는 문제(#341)

- 일시: 2026-09-07
- 대상 저장소 상태: 기존 코드 수정
- 축 점수: 목표 0.90 · 제약 0.90 · 완료 기준 0.70 · 기존 맥락 0.95 → 모호함 0.14

## 확정된 것

### 문제의 성격

- 결제 만료 조회가 `status = 'READY' AND createdAt < 임계`라, 결제를 다시 시작하면 앞 행이 `EXPIRED(SUPERSEDED)`가 되어 조회에서 빠지고 새 `READY` 행이 슬롯을 이어받는다. 조회가 보는 행이 항상 새것이라 임계를 못 넘는다. 개별 행의 `createdAt`이 갱신되는 것이 아니라 **조회 대상이 교체되는 것**이다.
- 방어 장치가 없다 — rate limit도 재시작 횟수 제한도 없다. 주문 생성 시점에 재고가 차감되므로 주문을 여러 개 만들어 각각을 한 시간에 한 번씩 살려두면 재고가 통째로 묶인다. 정합성 문제가 아니라 **재고 소진 경로**로 다룬다.
- 원인은 하나다: 결제 만료 시계가 **행 단위**라 사용자가 새 행을 만들어 조회 대상을 갈아치울 수 있다.

### 재결제 정책

- `IN_PROGRESS`·`UNKNOWN`일 때 재결제는 **거부하고 기다린다**(현재 동작 유지). 허용하면 앞 승인이 성공이었을 때 한 주문에 승인이 둘 성립한다.
- `FAILED` 후 재결제는 **허용을 유지한다.** `FAILED`는 활성 슬롯을 쥐지 않아 주문 만료를 막지 못하므로 이 문제의 원인이 아니다. 재결제를 반복해도 주문은 자기 만료 기준을 채우면 만료된다.
- 재결제 허용 여부를 가르는 기준은 상태 이름이 아니라 **돈이 움직였는지 아는가**다. 이 기준이 이미 일관되게 서 있으나 어디에도 문장으로 적혀 있지 않고 `PaymentStatus.holdsActiveSlot()`과 `yieldActiveSlot`의 분기에 나뉘어 있다.

### 주문 상태

- `OrderStatus`에 결제 진행 상태를 **추가하지 않는다.** 결제가 종결되면 원래 상태로 되돌아오는 값이라 생명주기 상태가 아니다. 직교 축을 상태에 섞지 않는 선례가 있다(`ADR pr242`·`pr340`).
- 주문이 결제 진행 상황을 **소유하지 않는다.** 소유하면 담는 그릇과 무관하게 끄는 자리가 생기고(끄기 실패 시 주문이 갇힌다), 정본이 둘로 갈리고, 밖에 닿는 트랜잭션이 는다.

### 수정 방향

- 주문 만료 배치가 건너뛰는 대상을 `IN_PROGRESS`·`UNKNOWN`으로 좁힌다. `READY`는 주문 만료를 막지 않는다.
- 주문을 만료시킬 때 그 주문의 `READY` 결제를 같은 트랜잭션에서 `EXPIRED`로 종결한다. 종결은 payment가 자기 코드로 수행하고, order가 소유한 port에 위임 메서드를 더한다.
- 종결 코드를 새로 만든다 — `SUPERSEDED`·`SESSION_TIMEOUT`과 원인이 다르다.
- 경합은 `markInProgress()`와 `expire()`가 둘 다 `READY`에서만 출발한다는 점을 이용해 `Payment`의 낙관 락으로 가른다. 어느 쪽이 이기든 돈이 나가지 않는다.
- 락 순서는 order → payment로 `PaymentApprovalService`와 맞춘다.

### 이 방향을 택한 이유

- 다른 두 안(결제 시작 거부 / 최초 결제 행 시각 기준)도 문제를 닫지만, 재고 회수 시점이 결제 만료 임계에 묶인 채다(약 130분). 결제 만료 임계는 방치된 결제창을 정리하는 값이지 재고를 위한 값이 아니다.
- 이 방향은 재고 회수를 주문의 시계 하나로 결정한다(약 65분).

## 드러난 가정

- 두 aggregate를 한 트랜잭션에서 바꾸는 것은 이 저장소가 이미 하는 일이며(`PaymentApprovalService`), 이번 변경도 그 형태를 따른다. `ADR pr342`의 "경계가 깨진다"는 그 PR의 범위 판단이지 금지 결정이 아니라고 본다.
- port에 종결 위임을 더해도 의존 방향은 그대로다 — order는 자기가 정의한 인터페이스에 대고 말하고 payment를 import하지 않는다.
- 결제 시작 응답과 만료 배치 모두 외부 계약이 바뀌지 않으므로 `docs/api-spec.md` 동기화는 없다고 본다(Design에서 확인).

## 남은 미확정

- 재고 회수 상한(약 65분)을 완료 기준에 수치로 명시할 것인가.
- 주문 만료 기준(60분)과 결제 만료 임계(60분)가 같은 값인 것을 그대로 둘 것인가. 값 조정은 이슈가 범위 밖으로 두었으나, 두 값의 관계를 문서로 못 박을지는 정하지 않았다.
- 밖까지 바꾸는 트랜잭션 자리를 어디에 어떤 이름으로 둘 것인가. **위험영역(상태 전이)** — Design에서 확정한다.
- port의 모양. 지금은 `orderId 집합 → 막힌 orderId 집합`인데 종결 위임이 붙으면 형태가 달라진다. **위험영역(상태 전이)** — Design에서 확정한다.

## 후속으로 뺄 것

- 만료 기준을 넘긴 주문에 결제창을 띄우지 않는다(`Order.checkPayable()`에 시간 판정 추가). 회원 경험 개선이라 목적이 다르다. 별도 이슈.
- 재결제 허용 기준("돈이 움직였는지 아는가")을 문장으로 남기는 것.
