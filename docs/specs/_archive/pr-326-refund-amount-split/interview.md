# 인터뷰 기록 — 결제의 환불 금액을 열린 총액과 성공 총액으로 가른다

- 일시: 2026-08-31
- 대상: 기존 코드 수정 (payment 도메인)
- 근거 이슈: #323
- 활성 방법론: ddd, bdd
- 축 점수: 목표 0.95 · 제약 0.95 · 완료 기준 0.90 · 기존 맥락 0.95 → 모호함 0.06

## 확정된 것

- **컬럼 둘로 가른다.** `total_refunded_amount` → `refund_opened_amount`(이름만 변경, 뜻·값 그대로) + `refund_succeeded_amount`(신설).
- **이름을 이렇게 고른 이유.** `opened`·`succeeded` 둘 다 생애 단계를 가리키는 과거형이고 둘 다 단조 증가하는 사건 누계라, 종류가 맞아 포함 관계가 생애 순서에서 따라온다. `ready`는 `RefundStatus.READY`와 짝지어 보여 상태별 분할로 오해된다(실제로 대화 중 그 오해가 일어났다). `total_*`은 한쪽이 집계 방식을, 다른 쪽이 생애 단계를 가리켜 축이 어긋난다.
- **파생값은 컬럼으로 두지 않는다.** 한도 = 승인액 − opened, 처리 중인 금액 = opened − succeeded, 결제사 잔액 추정 = 승인액 − succeeded.
- **한도 판정 결과는 안 바뀐다.** `opened`가 옛 누적 환불액과 값이 같다.
- **갱신 방식은 도메인 메서드 + 낙관 락(D).** `RefundService.complete` 안에서 결제를 로드해 도메인 메서드로 올리고 `saveChecked`에 맡긴다. 조건부 UPDATE(B)를 쓰지 않는다 — 덮어쓰기를 막으려면 버전을 올려야 하는데, 올리는 순간 조건부 UPDATE의 이점이 사라지고 불변식이 SQL에 살아 ddd 검사와 어긋난다. 같은 이유로 되돌린 선례가 있다(PR#245).
- **운영 데이터가 없다(pre-prod).** 컬럼 이름 변경을 RENAME으로 단순하게 하고, 기존 행을 옮기는 backfill은 실제로 옮길 행이 없어도 스크립트를 올바르게 쓰고 테스트로 검증한다.
- **결제 행 버전 충돌은 지금 구조대로 삼키고 대사에 맡긴다.** 갈라서 다르게 해도 할 수 있는 일이 "다시 시도"뿐인데 대사가 이미 그것을 하고, 대사의 마지막 창은 집는 횟수 상한이 없어 포기하지 않는다. 다만 거짓이 되는 주석·로그 문구는 사실에 맞게 고친다 — "같은 결과로 옮겨졌다"가 아니라 "먼저 옮겨졌거나, 결제가 동시에 바뀌어 이번 확정이 밀렸다"이다.
- **트랜잭션 경계는 D가 정한다.** 환불 완료 전이와 결제 집계 갱신이 한 트랜잭션이다. 나뉘면 환불만 성공으로 커밋되고 결제 집계가 안 올라가 영구 불일치가 된다.

## 코드로 확인한 것 (재조사 불필요)

- **`refund_succeeded_amount`를 올리는 자리는 하나뿐이다.** `Refund.complete()`가 `IN_PROGRESS`·`UNKNOWN`에서만 허용되고 `MANUAL_REVIEW`에서 나가는 전이가 코드에 없다. 즉 `RefundService.complete` 한 곳만 고치면 된다.
- **`RefundService`는 지금 결제를 전혀 로드하지 않는다.** 클래스 javadoc이 "환불만 로드하고 결제를 건드리지 않는다"고 명시한다 — 이 문장이 이번 변경으로 사실과 달라진다.
- **충돌 시 수렴 경로가 이미 있다.** `ExecuteRefundUseCase.transition`과 `ReconcileRefundUseCase.complete`가 둘 다 `PaymentException`을 삼키고 로그만 남긴다. 환불이 `IN_PROGRESS`로 남아 대사가 다시 집어 결제사 이력을 읽고 다시 확정한다.
- **`@DynamicUpdate`가 저장소에 한 곳도 없다.** 변경 감지가 UPDATE를 낼 때 SET 절에 전체 컬럼이 들어간다.
- **낙관 락 충돌은 `PAYMENT_CONCURRENTLY_MODIFIED`·`REFUND_CONCURRENTLY_MODIFIED`로 변환된다**(각 adapter의 `saveChecked`).

## 드러난 가정

- 불변식 `succeeded ≤ opened ≤ 승인액`은 구조상 저절로 성립한다 — 각 환불이 열릴 때 `opened`를 올리고, 그 환불이 성공할 때 같은 금액만큼 `succeeded`를 올리기 때문이다. 방어 검사를 도메인에 둘지는 설계 판단으로 남긴다.
- 운영 데이터가 없다는 전제는 두지 않는다. 기존 행을 옮기는 마이그레이션을 쓴다.

## 남은 미확정

- 경합 시나리오의 기대 결과(환불 생성과 환불 성공이 겹쳤을 때 무엇이 남아야 하나)를 문장으로 어떻게 적을지는 Scenarios에서 확정한다. 방향은 정해졌다 — 진 쪽은 롤백되고 대사가 다시 집어 결국 같은 최종 상태에 이른다.
- 위험영역 미확정 없음.
