# 데이터 모델: refund-amount-split

> 무엇이 존재하고 어떻게 바뀌는가. 물리 스키마는 `db-schema.md`에 있다.

## 결제가 드는 두 값

| 값 | 뜻 | 언제 오르나 | 줄어드나 |
| --- | --- | --- | --- |
| 돌려주기로 한 금액 | 이 결제에 열린 모든 환불 금액의 합 | 환불을 열 때, 그 환불 금액만큼 | 아니다 |
| 실제로 돌아간 금액 | 그중 성공으로 확정된 환불 금액의 합 | 환불이 확정될 때, 그 환불 금액만큼 | 아니다 |

둘 다 **단조 증가**한다. 환불이 실패하거나 사람에게 넘어가도 돌려주기로 한 금액은 줄지 않는다 — 그 몫을 풀어 주면 아직 돈이 안 돌아갔는데 새 환불이 끼어든다.

## 불변식

```
0 ≤ 실제로 돌아간 금액 ≤ 돌려주기로 한 금액 ≤ 승인 금액
```

오른쪽 두 관계가 왜 성립하는가.

- **돌려주기로 한 금액 ≤ 승인 금액** — 환불을 열 때 한도를 검사한다. 지금도 그렇다.
- **실제로 돌아간 금액 ≤ 돌려주기로 한 금액** — 환불 하나가 열릴 때 돌려주기로 한 금액을 올리고, 그 환불이 성공할 때 **같은 금액만큼** 실제로 돌아간 금액을 올린다. 금액은 만들어진 뒤 바뀌지 않고, 한 환불은 한 번만 성공한다.

승인 금액은 한 번 정해진 뒤 줄지 않는다 — 승인 금액을 담는 것은 상태 전이가 아니라서 결제가 어느 종착에 이른 뒤에도 다시 담길 수 있고 코드가 그것을 막지 않지만, 실시간 응답이든 이력 조회든 **같은 결제에 대한 결제사 응답**이라 같은 값이 다시 쓰인다. 이 전제가 깨지면 위 불변식이 소급해 깨진다.

## 파생값 — 저장하지 않는다

```
환불 한도            = 승인 금액 − 돌려주기로 한 금액        (지금도 이 계산이다)
아직 안 돌아온 금액   = 돌려주기로 한 금액 − 실제로 돌아간 금액
결제사 잔액 추정      = 승인 금액 − 실제로 돌아간 금액
```

뒤 둘은 이번에 코드로 만들지 않는다. 읽는 곳이 없고, 값은 두 금액으로 언제든 계산된다.

## 누가 언제 바꾸는가

```
환불을 연다        돌려주기로 한 금액 += 금액        결제의 도메인 메서드. 지금도 여기서 한다
환불이 확정된다     실제로 돌아간 금액 += 금액        결제의 도메인 메서드. 새로 생긴다
그 밖의 모든 것     아무것도 안 바꾼다
```

**"그 밖의 모든 것"이 이 표의 절반이다.** 이유가 둘로 갈린다.

- 환불의 결과 불명·검토 대기·재시도 전이, 대사 부기값과 통지 시각 갱신 — 건드리면 대사가 한 바퀴 돌 때마다 결제 버전이 오른다. 지금은 그 위에서 회원 요청이 밀리는 데까지 가지 않지만(미결 환불이 있으면 회원 취소가 한도 검사에서 먼저 막힌다) 부분취소가 들어오면 간다.
- 결제 자신의 상태 전이 — 두 금액은 상태와 직교한다. 종결됐는지는 얼마가 열렸고 얼마가 돌아갔는지와 무관하다.

## 두 값을 지키는 것

**같은 트랜잭션.** 환불을 성공으로 옮기는 것과 실제로 돌아간 금액을 올리는 것이 한 트랜잭션에서 커밋된다. 나누면 환불만 성공으로 남고 그 금액이 안 올라 영구히 어긋난다.

**환불의 상태 가드.** 환불 성공 전이는 응답 대기·결과 불명에서만 허용된다. **앞 확정이 이미 커밋된 뒤에** 다시 오는 확정을 여기서 거부한다.

**환불 행의 낙관 락.** 둘이 **같은 시점에** 그 환불을 읽어 동시에 확정하면 상태 가드는 양쪽 다 통과시킨다 — 자기 트랜잭션이 읽은 값을 보기 때문이다. 그때 한쪽을 되돌리는 것이 이 락이다. **이중 계상을 막는 것은 이 둘이며 경우가 다르다.**

**불변식 가드.** 이번 금액이 0보다 큰지, 그리고 실제로 돌아간 금액에 그것을 더한 값이 돌려주기로 한 금액을 넘지 않는지를 검사하고 어기면 거부한다(왜 둘을 함께 보는지는 결정 기록 3번). **이것은 이중 계상 방어가 아니다** — 환불이 둘 이상 열려 있으면 같은 환불이 두 번 계상돼도 총량이 한도를 안 넘어 통과한다. 총량이 깨진 것을 뒤늦게라도 잡는 안전망이며, 거부는 경합·재확정과 구분되는 실패 값으로 나간다.

**결제 행의 낙관 락.** 돌려주기로 한 금액을 올리는 것과 실제로 돌아간 금액을 올리는 것이 같은 행을 바꾸므로, 둘이 동시에 오면 한쪽이 진다. 서로 다른 환불이 동시에 확정될 때도 이 락이 잡는다. 다만 **같은** 환불의 동시 확정은 환불 전이를 먼저 저장하기로 정해 앞의 환불 행 락이 먼저 잡는다. 진 쪽은 자기 트랜잭션이 통째로 되돌려진다. 이 버전 갱신을 생략하면 다른 트랜잭션의 저장이 이 값을 옛 값으로 덮는다 — 변경 감지가 UPDATE를 낼 때 모든 컬럼을 쓰기 때문이다.

## 상태와의 관계

두 금액은 **결제 상태와 직교한다.** 종결된 결제의 금액도 오를 수 있어 그 금액을 올리는 도메인 메서드는 결제 상태를 조건으로 삼지 않는다(근거는 결정 기록 3번).

환불 쪽 상태 전이는 바뀌지 않는다.

```
READY ─→ IN_PROGRESS ─┬─→ SUCCEEDED
                      ├─→ UNKNOWN ─┬─→ SUCCEEDED     ← 성공으로 가는 두 전이만
                      │            │                    결제를 함께 바꾼다
                      │            └─→ MANUAL_REVIEW
                      └─→ MANUAL_REVIEW

MANUAL_REVIEW 에서 나가는 전이는 없다.
```

성공으로 가는 길이 둘(응답 대기에서, 결과 불명에서)이지만 **그 둘이 같은 한 메서드**를 지나므로 실제로 돌아간 금액을 올리는 자리는 하나다.

## 이 값이 답하지 못하는 것

이 값이 세는 것은 **결제사 응답으로 확정된 돈**이지 실제로 나간 돈이 아니다. 둘이 어긋나는 길이 **양쪽으로** 있다.

```
작아지는 쪽   ① 검토 대기에서 나가는 전이가 없어, 운영자가 결제사 콘솔에서
                직접 돌려준 건이 우리 기록에 안 들어온다
             ② 우리 시도 키가 안 실린 취소가 이력에 있으면 알리기만 하고
                환불 행을 만들지 않아, 그 돈은 아예 세지 않는다
커지는 쪽     ③ 결제사가 "아직 안 끝났지만 곧 자동으로 다시 처리한다"고 답한 건을
                성공으로 접으므로, 돈이 나가기 전에 값이 오른다
```

③은 결제사 명세가 재시도하지 말라고 지시해 그렇게 정한 기존 결정이다. 셋 다 이 작업의 범위 밖이며, **값을 읽는 쪽은 어긋남이 한 방향이라고 가정하면 안 된다.**

두 값을 되돌리는 길도 없다. 도메인 메서드가 올리기만 하므로, 값이 한번 잘못 부풀면 도메인 안에서 바로잡을 수단이 없다. 그때 손볼 수 있는 것은 운영 데이터를 직접 고치는 것뿐이며, 그 경로를 만드는 것은 이 작업의 범위 밖이다.
