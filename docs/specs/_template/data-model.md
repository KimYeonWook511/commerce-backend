# Data Model: <spec-name>

> 이 문서는 **도메인(개념) 계층**이다 — 무엇이 존재하고, 어떻게 식별되고, 어떻게 상태가 전이되는가.
> 물리 스키마(테이블·컬럼·인덱스·마이그레이션)는 `db-schema.md`가 다룬다. 둘은 층위가 다르다:
> 여기는 "주문이라는 엔티티가 어떤 규칙으로 사는가", db-schema는 "그걸 RDB로 어떻게 내리는가".
>
> `plan.md`의 하위 문서다. 데이터 모델을 다루지 않는 spec이면 이 문서를 만들지 않는다.
> **위험영역 주의**: 데이터 모델·식별 규칙·상태 전이는 `spec-constitution.md`의 불가침 영역이다.
> spec에서 미확정인 채로 여기서 임의 설계하지 않는다 — 확정은 Clarify(3)에서 끝나 있어야 한다.

## 엔티티

> 각 엔티티가 무엇을 나타내는지, 핵심 속성, Aggregate 경계.
> (`package-structure-conventions.md`: cross-aggregate 참조는 객체가 아니라 ID로, same-aggregate만 객체로.)

### <엔티티명>

- **역할**: 무엇을 나타내는가.
- **핵심 속성**: <속성: 의미>. (구현 타입이 아니라 도메인 의미 중심으로.)
- **식별·유일성**: 무엇으로 한 건을 구분하는가. 자연키/대리키, 유일성 제약.
- **Aggregate 경계**: 이 엔티티가 속한 Aggregate. 같은 Aggregate인 것 / ID로만 참조하는 것.

## 관계

- 엔티티 간 관계(1:N, N:M 등)와 방향. 어느 쪽이 소유하는가.
- cross-aggregate는 ID 참조임을 명시.

## 상태 전이 (lifecycle)

> 상태를 갖는 엔티티마다 전이 규칙을 적는다. **위험영역** — 비어 있으면 안 되고, 미확정이면
> spec 단계에서 마커로 남아 Clarify에서 확정됐어야 한다.
> (`package-structure-conventions.md`: 상태 변경은 setter가 아니라 규칙을 품은 메서드로만.)

### <엔티티명> 상태

- **상태 목록**: <초기> → <중간…> → <종료>.
- **전이 규칙**:
  | 전이 | 조건 | 비고 |
  | --- | --- | --- |
  | <상태A> → <상태B> | <어떤 조건/이벤트일 때> | |
- **불가 전이**: 명시적으로 금지되는 전이(예: 종료 상태에서 되돌아갈 수 없음).
- **동시성**: 동시 전이 충돌 시 처리(낙관 락 등). 상세는 db-schema·architecture와 연계.

## 불변식 (invariants)

- 항상 참이어야 하는 도메인 규칙(예: "수량 ≥ 1", "결제 완료 전 배송 불가"). 엔티티 생성·전이에서 강제되는 것.
