# API Spec: order-expiry-closes-ready-payment

> 이 작업이 바꾸는 계약만 적는다. 나머지는 루트 `docs/api-spec.md`가 정본이다.

## 바뀌는 것

**승인 요청의 실패 응답이 하나 는다.** 요청·성공 응답은 바뀌지 않는다.

| 그 결제 시도의 상태 | 응답 |
| --- | --- |
| 성공 | 200 + 앞서 확정된 결과 |
| 승인 결과 미확정(`IN_PROGRESS`·`UNKNOWN`) | `PAYMENT_RESULT_PENDING` (409) |
| **주문 만료로 종결됨** | **`PAYMENT_ORDER_EXPIRED` (409)** |
| 그 밖의 사유로 종결됨(실패·반려·대체 종결·결제 세션이 지난 종결) | `PAYMENT_ATTEMPT_CLOSED` (409) |
| 승인을 아직 부르지 않음(`READY`) | 결제사에 승인을 요청한다 |

이 표는 **소유 확인을 통과한 요청**에만 적용된다. 없는 결제 키와 남의 결제 키를 모두 같은 404로 접는 기존 판정이 이 표보다 앞에 서므로, 새 코드가 남의 주문이 만료됐다는 사실을 알려주지 않는다.

## 왜 가르나

`PAYMENT_ATTEMPT_CLOSED`의 안내는 **다시 시작하라**다. 그 시도로는 더 진행할 것이 없으니 새로 결제하라는 뜻이고, 대체 종결·결제 세션이 지난 종결에는 맞는다.

주문 만료로 종결된 경우에는 맞지 않는다. 그 주문은 이미 취소되어 결제 가능 여부 판정에 막히므로, 회원이 안내대로 다시 시작하면 또 막힌다. **할 일이 재결제가 아니라 재주문**이라 안내가 갈려야 한다.

## 범위

승인 요청이 그 결제를 **읽는 시점에** 종결이 보이는 경우다. 읽은 뒤에 만료가 커밋되면 승인 호출 직전 전이가 밀려 `PAYMENT_RESULT_PENDING`이 나가고, 회원이 다시 시도하면 그때는 종결이 보여 이 응답을 받는다.

## 안 바뀌는 것

- 결제 시작 요청·응답. 만료와 겹치면 두 갈래인데 어느 쪽도 새 응답이 아니다. 결제 시작이 만료 커밋 뒤에 주문을 읽으면 결제 가능 여부 판정에 막히는 기존 응답이 나간다. 결제 시작이 앞 결제를 읽은 뒤 만료가 그 결제를 종결해 커밋하면, 앞 결제를 대체 종결하는 갱신이 낙관 락에 져 기존 충돌 응답(409)이 나간다. 그 갱신이 만료 청크가 쥔 결제 행 잠금을 기다리다 DB의 잠금 대기 한도를 넘기면 기존 잠금 획득 실패 응답이 나간다. 충돌·잠금 실패 갈래는 이 작업으로 잦아진다. 회원이 다시 시도하면, 만료 청크가 커밋된 뒤에는 결제 가능 여부 판정에 막히는 응답을 받는다.
- 주문 만료는 배치라 밖으로 나가는 계약이 없다
