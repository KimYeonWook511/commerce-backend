# Architecture: order-expiry-closes-ready-payment

> 이 작업이 바꾸는 구조만 적는다. 바뀌지 않는 부분은 루트 `docs/architecture.md`가 정본이다.

## 흐름

```
OrderExpirationJobScheduler (presentation/scheduler)
  └─ orderExpirationJob → orderExpirationStep (presentation/batch)
       청크 트랜잭션 하나 — 아래 reader·writer가 모두 그 안에서 돈다
       ├─ reader   대상을 고른다
       │            OrderRepository        만료 기준을 넘긴 INIT 주문
       │            BlockingPaymentChecker 승인을 부른 뒤의 결제가 걸린 주문을 뺀다
       │
       └─ writer   반영한다 — 주문 하나씩
                    ExpireOrderService.expireOrder  @Transactional (청크 트랜잭션에 참여)
                      ├─ PaymentRepository.findActiveByOrderId(orderId)
                      ├─ 없으면 결제 단계를 건너뛴다
                      ├─ Payment.tryExpire(ORDER_EXPIRED)
                      │     false면 여기서 멈춘다 (만료하지 않는다)
                      ├─ PaymentRepository.save(payment)
                      ├─ Order.cancelBeforePayment()
                      └─ StockRestoreOutboxCreateService.createOutboxEvent()
```

## 반영이 보는 것

reader와 writer는 같은 청크 트랜잭션이라, 반영이 결제를 읽으면 **대상을 고른 시점의 스냅샷**을 본다(MySQL 기본 격리 수준 REPEATABLE READ).

| 대상을 고른 뒤 일어난 일 | 반영의 결말 |
| --- | --- |
| 있던 결제의 상태가 바뀌었다 | 결제 행 갱신은 최신 행의 버전을 비교하므로 낙관 락이 충돌한다. 다시 판정할 때 새 트랜잭션이 바뀐 상태를 본다 |
| 결제가 새로 생겼고 아직 승인 확정 전이다(`READY`·`IN_PROGRESS`·`UNKNOWN`) | 보이지 않는다. 주문만 취소되고 그 결제는 살아남는다. 그 결제의 승인 확정은 취소된 주문에 막혀 반려·환불로 수렴한다 — `spec.md` Edge Cases가 받아들인 창이다 |
| 결제가 새로 생겨 승인까지 확정됐다 | 결제는 보이지 않지만 주문은 이미 `PAID`로 바뀌었다. 주문 행 갱신이 최신 버전을 비교하므로 낙관 락이 반영을 실패시킨다. 같은 회차에 다시 판정하면 결제가 승인 성공이라 `tryExpire`가 `false`를 돌려줘 멈추고, 다음 회차에는 주문이 `PAID`라 대상에 들지 않는다 |

## 판정이 사는 곳

```
만료 반영    승인을 부른 뒤의 결제가 걸렸으면 만료하지 않는다
             → 종결 전이가 돌려준 boolean으로 멈춘다. 결제 상태로 분기하지 않는다

결제 도메인  승인을 아직 부르지 않은 결제만 종결할 수 있다
             → 종결 전이가 스스로 판정하고 됐는지를 돌려준다
```

만료 반영이 결제 상태로 분기하면 "승인을 아직 부르지 않은 것만 종결한다"는 규칙의 사본이 두 곳에 생기고, 도메인 쪽이 바뀔 때 만료 반영이 조용히 낡는다.

## 도메인 간 접근

| 무엇 | 방식 |
| --- | --- |
| 대상을 고를 때 막히는 주문을 묻는다 | port `BlockingPaymentChecker` — order가 정의하고 payment가 구현한다. 기존 그대로 |
| 반영할 때 결제를 종결한다 | `ExpireOrderService`가 `PaymentRepository`·`Payment`를 직접 다룬다. 같은 패키지의 `CancelPaidOrderService`와 같은 형태다 |

두 쪽이 만료를 막는 결제를 같은 집합으로 본다 — **승인을 부른 뒤의 결제**(`IN_PROGRESS`·`UNKNOWN`·`SUCCEEDED`). reader 조회는 활성 슬롯 열을 그대로 쓰고 `READY`만 뺀다. 같은 집합을 조회 조건과 결제 전이 두 자리에서 표현하고, 어긋나도 반영 시점의 결제 전이가 돈을 지킨다.

## 경합이 갈리는 자리

`READY`에서 나가는 전이는 다섯이다 — 승인 호출 직전 전이, 결제 시작의 대체 종결, 회수, 결제 세션이 지난 종결, 그리고 이번에 더하는 주문 만료 종결. 모두 `READY`에서만 출발하므로 결제 행 하나가 판정 지점이 된다. 목록과 각 상대에 대한 결말은 `spec.md`가 정본이다.

**충돌은 트랜잭션 안에서 잡지 않고 그대로 전파시킨다.** 결제 저장은 낙관 락 충돌을 도메인 예외로 번역하지 않는 `save`를 쓴다. 번역하면 배치가 선언해 둔 재시도가 그 예외를 못 알아보고 건너뛰기만 걸린다.

**충돌한 반영은 롤백되고 다시 판정된다.** 충돌이 writer 안에서 터지면 배치가 같은 회차에 청크를 다시 시도하고, 청크 커밋에서 터지면 그 회차가 실패해 다음 회차가 다시 고른다. 결말은 같고 판정 시점만 다르므로, 이 설계는 같은 회차 재시도에 기대지 않는다.

## 커밋 경계

만료 반영의 트랜잭션은 배치 청크 트랜잭션에 참여한다. **그래서 실제 커밋 경계는 주문 하나가 아니라 청크다.** 한 주문의 충돌이 그 청크를 통째로 되돌리고, 다시 판정하는 트랜잭션이 상대 전이를 본다. 재시도 한도를 넘기면 한 건씩 처리하고, 거기서도 지면 그 주문을 건너뛰는데, 건너뛰기 예산은 회차 전체가 공유하고 소진하면 그 회차가 실패해 다음 회차가 다시 본다. 결제 시작을 쉬지 않고 반복해 이 충돌을 일부러 일으키는 경우의 한계는 `spec.md` Edge Cases가 정한다.

결제 행 잠금도 청크가 커밋될 때까지 유지된다. 같은 결제의 승인 호출 직전 전이는 길어야 청크 하나만큼 기다린 뒤 충돌해 결과 확인 중 응답을 받는다. 그 사이 청크가 롤백되면 기다리던 쪽이 이기고 다시 판정한 반영이 그 결과를 따른다. 대기가 DB의 잠금 대기 한도를 넘기면 잠금 획득 실패 응답이 나간다 — 어느 쪽이든 결제사를 부르기 전이다.

## 잠금

만료 반영이 주문 행과 결제 행을 함께 바꾼다. 승인 확정 흐름도 그 둘을 바꾸지만 **쓰기가 어느 순서로 나가든 순환이 서지 않는다.** 승인 확정은 주문 행(FOR UPDATE) → 결제 행 순서다. 만료 반영의 쓰기가 주문 행부터 나가면 같은 방향이다. 결제 행부터 나가면, 그 갱신이 잠금을 쥔 채 진행하는 것은 최신 행이 `READY`일 때뿐이고 그때는 활성 슬롯이 주문당 하나라 같은 주문의 승인 확정이 설 수 없다. 최신 행이 `READY`가 아니면 그 갱신은 0행으로 실패해 반영이 끝난다. 이 논증은 한 주문 안의 것이다. 청크는 앞 주문들의 잠금을 쥔 채 진행하므로, 서로 다른 주문의 결제 행 둘을 결제 id 순으로 쓰는 회수와는 교착이 날 수 있다. 그때 DB가 한쪽을 되돌리고, 결말은 회차 실패이거나 회수가 지는 갈래다. 결제완료 주문 취소는 대상 주문 상태가 겹치지 않는다.

이 논증이 깨지는 변경(예: 결제완료 이후 흐름이 만료 대상 주문을 건드리게 되는 것)이 오면 잠금 순서를 명시적으로 맞춰야 한다.

## 함께 고치는 것

- `BlockingPaymentCheckerAdapter`의 판정 기준 서술이 뒤집힌다. 지금 "결제창을 띄운 것부터 결과를 모르는 것까지 전부 막힌 것으로 본다"고 적혀 있는데, 승인을 아직 부르지 않은 결제는 더 이상 막지 않는다
- `PaymentRepository`의 조회 메서드 이름이 조건과 어긋나게 된다. 활성 슬롯을 쥔 결제 전부가 아니라 승인을 부른 뒤의 결제를 찾는다
- 조회 조건은 활성 슬롯 열을 그대로 쓰고 `READY`만 뺀다. 기존 유일 인덱스를 그대로 탄다
