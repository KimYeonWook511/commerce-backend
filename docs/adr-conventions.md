# ADR 컨벤션

이 문서는 commerce-backend에서 ADR(Architecture Decision Record)을 작성·관리하는 규칙을 정의한다.

ADR은 `docs/adr/`에 **결정 1개 = 파일 1개**로 보관하고, `log4brains preview`로 검색 가능한 사이트에서 본다. 도구 설치·빌드 방법은 아래 "log4brains로 보기"를 참고한다.

## ADR이란

기능을 구현·수정하면서 내린 **중요한 기술적 결정**을 그 **이유와 함께** 기록하는 짧은 문서.
코드는 "무엇을(what)" 했는지는 보여주지만 "왜(why)"는 남기지 않는다. ADR이 그 "왜"를 기록한다.

핵심 원칙: **ADR은 불변(immutable)이다. 바뀌는 건 status뿐.**
생각이 바뀌면 기존 문서를 수정하지 않고, 새 ADR을 작성해 기존 ADR을 대체(supersede)하면서 기존 결정의 이력을 보존한다.

## 무엇을 ADR로 남기나

| 기록 위치 | 무엇을 |
| --- | --- |
| 코드 주석 | "이 줄에서 왜 이렇게 했나" (지역적, 코드와 함께 사라짐) |
| 커밋 / PR 설명 | "이 변경을 왜 했나" (특정 변경에 묶임) |
| **ADR** | "이 시스템을 왜 이런 방향으로 짓나" (전역적, 코드보다 오래 삶) |
| 컨벤션 문서 | "지금 따라야 할 규칙" (ADR의 결정이 여기 반영됨) |

> 코드 주석·테스트명은 **자립적**으로 쓴다 — ADR 번호나 작업 문서의 내부 식별자를 코드에 남기지 않는다. 작업 문서는 시간이 지나면 아카이브되고 코드만 남으므로, 코드에 적힌 그 ID는 독자에게 무의미해진다. "왜"는 ID 없이 문장으로 설명한다.

자가 점검: **"6개월 뒤 누가 이걸 멋모르고 되돌렸다가 사고 날까?"** → 그렇다면 ADR.
ADR은 최소한으로 작성한다. ADR로 남길지 망설여지는 결정은 ADR로 남기지 않는다.

## 파일 구조

```
docs/
├── adr-conventions.md       ← 이 문서 (작성 규칙)
└── adr/                      ← 실제 ADR (결정 1개 = 파일 1개)
    ├── README.md             ← 레거시(구 adr.md ADR-NNN 번호) → 파일 매핑
    ├── template.md
    └── YYYYMMDD-pr<번호>-<slug>.md
```

- 단일 파일에 누적하지 않는다. **결정 1개당 파일 1개.** (단일 파일은 머지 충돌의 원인)
  - 이것은 `docs/adr/`에 적용된다. **작업 중 임시로 모아 두는 곳은 예외**이며, 아래 "작업 중 결정의 staging"이 정한다.
- 인덱스는 손으로 관리하지 않는다. **log4brains가 자동 생성** (아래 참조).

## 파일명 규칙

```
docs/adr/20260622-pr245-payment-escalation-retry.md
```

- `YYYYMMDD` — 결정/작성 날짜. log4brains가 타임라인 정렬에 쓰는 필수 prefix.
- `pr<번호>` — 그 결정이 나온 PR 번호 (소문자 `pr`). 추적성 식별자. self-documenting.
- `<slug>` — kebab-case 핵심 명사. grep 검색 앵커.
- 제목은 **결정을 단언**하는 한 문장. (주제형 X "캐시에 대하여" / 동사형 O "캐시는 RDB 커밋 이후 실행한다")
- 다른 문서에서 참조할 땐 `PR#245`로 짧게. 마크다운 링크는 supersede Status 줄에서만 쓴다.

## ADR 본문 구조 (Nygard 형식)

- **Title** — 결정을 단언하는 한 문장
- **Status** — proposed / accepted / superseded
- **Context** — 어떤 상황·제약 때문에 필요했나
- **Decision** — 무엇을 결정했나
- **Consequences** — 얻는 것과 감수하는 trade-off

부분 대체(기존 결정의 일부 메커니즘만 갱신)는 status를 바꾸지 않고, 기존 ADR 본문에 어느 부분이 어떤 PR로 갱신됐는지 한 줄로 명시한다. status의 `superseded`는 결정 전체가 대체됐을 때만 쓴다.

## 작업 중 결정의 staging

**spec-harness로 진행하는 작업**은 결정을 그 작업의 spec 폴더(`docs/specs/<spec명>/adr.md`)에 모았다가 마지막에 루트로 옮긴다. **그 밖의 작업**은 결정이 확정되는 PR에서 `docs/adr/`에 파일을 직접 추가한다.

| | staging | 루트 승격 |
| --- | --- | --- |
| harness 작업 | `docs/specs/<spec명>/adr.md`에 결정이 생길 때마다 이어 쓴다 | Root Sync 단계에서 한 번에 |
| 그 밖 | 없다 | 그 PR에서 `docs/adr/`에 바로 |

- **staging 파일은 단일 파일이다.** 위 "결정 1개 = 파일 1개"는 `docs/adr/`에 적용되고, staging은 작업 중 임시 보관이라 해당하지 않는다. **그 폴더는 `.gitignore` 대상이라 추적되지도 않는다.**
- **staging의 번호는 그 작업 안에서만 통한다.** 승격할 때 결정 하나가 파일 하나가 되고, 파일명은 위 "파일명 규칙"을 따른다. staging 번호는 그때 사라진다.
- **승격은 append만 한다.** 루트 ADR을 수정·삭제하지 않는다. 기존 결정을 대체하면 새 파일에 supersede 관계를 적고 **옛 파일은 Status 한 줄만** 바꾼다.
- **staging 파일 자체도 함께 보존된다.** 작업 기록을 `docs/specs/_archive/`로 승격할 때 딸려 가며, 그 사본은 **"이 작업이 그 결정에 어떻게 도달했나"의 맥락**이다. 루트 ADR이 결정의 정본이고 그쪽은 참고 자료다.
- **staging에 쌓는 시점은 결정이 나는 때다.** 마지막에 몰아 쓰지 않는다 — 그러면 왜 그렇게 정했는지가 이미 흐려져 있다.

## log4brains로 보기

ADR을 검색 가능한 정적 사이트로 변환한다. 인덱스를 자동 생성하므로 README 수작업이 필요 없다.

```bash
npm install -g log4brains   # 최초 1회 설치 (node 필요)
log4brains preview          # 로컬에서 검색·타임라인으로 봄 (상시 서버 불필요)
log4brains build            # 정적 사이트로 빌드 (배포용, .log4brains/에 산출)
```

- `.log4brains/`(빌드 산출물)는 `.gitignore`, `.log4brains.yml`(설정)은 커밋한다.
- 파일명이 `YYYYMMDD-`로 시작하면 log4brains가 ADR로 인식한다. 이 문서(`adr-conventions.md`)처럼
  날짜로 시작하지 않는 파일은 ADR로 잡히지 않으므로 사이트에 영향 없다.

## 의미적 충돌

파일을 분리하면 서로 다른 결정이 각각 다른 파일로 추가되므로 git 머지 충돌은 발생하지 않는다.
그러나 git이 잡지 못하는 충돌이 있다: 파일은 겹치지 않으나 **결정 내용이 서로 모순되는 경우**다.

- 같은 기존 ADR을 두 작업이 서로 다른 방향으로 뒤집으면(supersede), 두 결정은 양립할 수 없다.
- git은 텍스트 겹침만 보므로 이 모순을 자동으로 탐지하지 못한다.

따라서 새 ADR이 기존 ADR을 대체·수정할 때는 어떤 ADR을 건드리는지 Status 줄과 본문에 명시한다.
같은 기존 ADR을 둘 이상의 작업이 건드리면, 그 모순 여부는 사람이 직접 판단한다.
