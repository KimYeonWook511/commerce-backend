# PR 컨벤션

이 문서는 현재 Repo에서 PR을 작성할 때 따르는 규칙을 정의한다.

## base 브랜치

- PR은 `develop`을 base로 생성한다.
- `main`으로 직접 PR을 올리지 않는다.

## PR 제목 형식

```text
<type>: <요약>
```

## 허용 타입

- `feat`: 사용자 또는 운영자가 사용할 수 있는 기능 동작을 추가하거나 기존 기능 범위를 확장할 때 사용한다.
- `fix`: 의도와 다르게 동작하던 버그를 고칠 때 사용한다.
- `refactor`: 외부 동작 변화 없이 구조, 이름, 책임 분리, 중복 제거를 정리할 때 사용한다.
- `test`: 테스트 코드, fixture, 설정만 추가하거나 수정할 때 사용한다.
- `docs`: 문서만 변경할 때 사용한다.
- `chore`: 제품 기능이 아니라 개발/운영/자동화 기반을 변경할 때 사용한다. 하네스, AI 도구 설정, CI, PR 템플릿, Docker/샌드박스 환경, Gradle 설정, 코드 리뷰 설정은 `chore`를 사용한다.

## 타입 선택 기준

- PR의 주된 변경 목적을 기준으로 선택한다.
- 기능 구현이 주 목적이면 문서 수정이 함께 있어도 `feat`를 사용한다.
- 문서만 고치는 PR은 `docs`를 사용한다.
- 하네스나 자동화 변경이 주 목적이면 `chore`를 사용한다.

## 요약 규칙

- 명사형으로 작성한다.
- 마침표(`.`)로 끝내지 않는다.
- PR의 주된 변경 목적을 한 줄로 표현한다.

예:
- `feat: 상품 조회 API 추가`
- `fix: 인증 토큰 만료 처리 수정`
- `refactor: 결제 승인 서비스 책임 분리`
- `test: 인증 컨트롤러 예외 응답 테스트 추가`
- `docs: 상품 조회 API 문서 보강`
- `chore: Claude Code 컨텍스트 엔지니어링 하네스 구축`

## Draft PR

작업이 아직 진행 중이거나 리뷰 준비가 되지 않은 경우 draft PR로 생성한다.

draft PR을 사용하는 경우:
- 구현이 완료되지 않아 추가 작업이 남아 있는 경우
- 테스트가 아직 작성되지 않은 경우
- 방향성 검토나 초기 피드백이 필요한 경우

draft가 아닌 PR을 생성하는 경우:
- 구현과 테스트가 완료되어 바로 리뷰 가능한 경우

## 머지 규칙

- 머지 방식은 squash and merge를 사용한다.
- 머지 commit 제목은 PR 제목을 그대로 사용한다 (`<type>: <요약> (#N)` 형태로 자동 부착).
- Extended description은 각 commit의 subject만 남기고 body는 제거한다. PR 본문이 이미 변경 맥락을 담고 있으므로 git history에는 압축된 요약만 남긴다.
- CLI로 머지하는 경우 `gh pr merge <N> --squash` 를 사용한다. body가 들어가 있다면 `--body`로 정리된 내용을 명시하거나, 정리가 필요하면 GitHub UI에서 수동 편집 후 머지한다.
- `## 후속 작업` 섹션은 본 PR의 머지 조건이다. 모든 항목이 체크되지 않은 상태에서는 머지하지 않는다. agent가 머지를 부탁받았을 때 미체크 항목이 있으면 머지를 보류하고 사용자에게 보고한다.
- 본 PR 작업 중 발견되어 별도 issue로 등록만 한 무관한 작업(본 PR의 머지 조건이 아닌 항목)은 PR 본문 어디에도 적지 않는다. `## 관련 이슈`는 본 PR이 해결하는 이슈만, `## 후속 작업`은 머지 조건인 항목만 적는다. 무관 이슈는 자체 issue로 추적되므로 PR에서 다시 연결할 필요가 없다.
- agent가 머지를 부탁받은 경우에도 위 모든 룰을 동일하게 따른다.

## 본문 작성 기준

PR 템플릿(`.github/pull_request_template.md`)을 기준으로 작성한다.

### 요약

- PR에서 무엇을 왜 변경했는지 bullet 형식으로 작성한다.
- 구현 세부사항보다 변경 의도와 결과를 중심으로 서술한다.

### 변경 사항

- 주요 파일 또는 모듈 단위로 변경 내용을 나열한다.
- 파일명이나 경로를 인라인 코드로 표기한다.

### 문서/하네스 변경

- 변경한 항목만 체크한다.
- 해당 없으면 `해당 없음`만 체크한다.
- 체크하지 않은 항목을 임의로 제거하지 않는다. 모든 체크박스를 유지한다.
- 템플릿에 없는 항목이라도 필요하면 새 항목을 추가할 수 있다.

### 테스트

- 테스트를 실행했으면 어떤 범위를 실행했는지 명시한다.
- 실행하지 않았으면 사유를 반드시 적는다.
- 체크하지 않은 항목을 임의로 제거하지 않는다. 모든 체크박스를 유지한다.

### 참고

- 설계 결정, 관련 이슈, 주의사항 등 리뷰어에게 필요한 추가 맥락을 작성한다.
- 없으면 생략해도 된다.
