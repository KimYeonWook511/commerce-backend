# 기능 ADR

## 결정 제목

- 관리자 재고 관리는 상품 API와 분리하고, 재고 변경 이력을 별도 테이블에 저장한다.

## 배경

- 상품 관리 feature는 상품 등록/수정/삭제 책임만 가지며 상품 등록 시 재고 레코드를 생성하지 않도록 완료되었다.
- 재고 관리는 주문 경로의 정합성과 운영 추적성을 함께 고려해야 하므로 상품 command API에 합치면 책임이 커진다.
- 재고 이력은 변경 사유와 변경 주체를 보존해야 하므로 현재 수량만 가진 `tbl_stock`만으로는 요구사항을 충족할 수 없다.

## 결정 내용

- 초기 재고 생성은 `POST /admin/products/{productId}/stock` 별도 API로 제공한다.
- 관리자 재고 증가는 `POST /admin/products/{productId}/stock/increase`, 감소는 `POST /admin/products/{productId}/stock/decrease`로 분리한다.
- 재고 변경 이력은 신규 `tbl_stock_history`에 저장한다.
- 변경 주체는 인증된 관리자 member id를 `admin_member_id`로 기록한다.
- 변경 수량은 증가 양수, 감소 음수로 기록한다.

## 근거

- 기존 상품 등록 API 계약을 변경하지 않아 완료된 상품 관리 feature의 영향 범위를 줄일 수 있다.
- 증가/감소 API를 분리하면 요청 의도가 명확하고 각 API의 validation과 테스트가 단순하다.
- 이력 테이블을 별도로 두면 현재 재고 수량과 운영 감사 데이터를 분리해 관리할 수 있다.
- 인증 컨텍스트의 관리자 member id를 사용하면 클라이언트가 주체를 임의로 전달하는 문제를 피할 수 있다.

## 결과

- 관리자 재고 기능은 상품 관리와 분리된 독립 feature로 확장된다.
- 재고 생성은 상품 생성 후 별도 호출이 필요하다.
- 첫 버전의 이력 조회는 pagination 없이 전체 목록을 반환하므로 대량 데이터 최적화는 후속 작업에서 검토한다.
