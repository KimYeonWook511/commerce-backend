# 태스크 ADR

## 개요

본 태스크는 동작 변화가 없는 식별자 정리 및 MDC 조작 캡슐화 리팩토링이다. 신규 기술 스택 선택, 외부 계약 변경, 트레이드오프 결정이 없으므로 별도 ADR 항목을 생성하지 않는다.

## 본 태스크에서 ADR을 작성하지 않는 이유

- 기능 변화 없음: 외부 API, 로그 포맷, 응답 헤더, MDC 키 값, traceId 정규식 모두 변경되지 않는다.
- 기술 선택 없음: 새 라이브러리·프레임워크·통신 방식·저장소를 도입하지 않는다.
- 호환성 고려 없음: 기존 호출처 전체가 같은 PR에서 컴파일러 차원에서 갱신된다. 외부 시스템 의존 없음.
- 두 가지 후보 사이의 결정 수준이 ADR을 요구하지 않는다. `LogContext` 단일 클래스 통합·`com.commerce.common.log` 패키지 위치·상수 `private` 처리·MDC 조작 메서드 캡슐화는 모두 본 태스크 PRD/architecture에 근거가 명시되어 있으며 회귀 위험이 없다.

## 참고: 관련된 기존 ADR

- ADR-017(Kafka traceId 전파 설계 결정, `docs/adr.md`): 본 태스크에서 코드 식별자만 갱신되며 ADR 결정 내용은 그대로 유효하다. ADR-017 본문은 동작 기준으로 작성되어 있어 갱신이 필요 없다.

## 추후 ADR이 필요해지는 시점

- MDC 키 경계를 도메인 식별자(`orderId`, `paymentId` 등)로 확장하면서 키 전파·정리 정책에 새로운 트레이드오프가 생길 때.
- traceId 헤더 이름·정규식 패턴을 변경(예: W3C `traceparent` 전환)할 때.
- `LogContext`를 다른 모듈(예: `commerce-common-lib`)로 분리할 때.
